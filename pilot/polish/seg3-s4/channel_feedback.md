## 五、fable-wf 报回的四条真问题（段末必须处理）

派发词里「反馈歧义处」那一条又一次产出了实质内容（SEG-1 准入小考时它报出过 8 条真问题）。

### 1. ⚠ 工装缺陷：锁清单只按 anchors 的 **id** 命中，不做 **jp 字面**比对

`739`（b93）与软锁锚点 `13440` 的 jp **全同**，但 739 不在 `locked.json` 的
`soft_ids` 里——形式上它是可随便改的普通行，**改了必然打破锚点逐字一致**。
本轮 fable-wf 自己按锚点维持住了并在 note 登记，但**这是运气不是闸**。

建议：`polish_setup` 生成锁清单时，把「jp 与任一锚点句字面全同的非锚点 id」也纳入
`soft_ids`（或至少单列一档提示）。这条对后续每一段都成立。

### 2. 跨章「提请下游」的传递链是断的：`12380` 结ばれる 母题

crd 纪要 batch 97 明确点名 `3834 / 12380 / 15900 / 15921 / 15922` 须同作「走到一起」
（「散译会散掉」），但更晚翻译的 b111 落笔时没执行，b111 自己的纪要也没提。
fable-wf 已就此 `adjudicate=true` 并给出建议稿。

它还提示同型漏网可能不止一处（点名 batch 62 的 `15768/15769` 两思い句族）。
**建议段末用「提请下游」条目做一次机械比对**，而不是靠执行通道逐段撞见。

### 3. jp 全等孪生块 / 跨批引用耦合：须**捆绑裁决**

- `b96` 与 `b98` 有一段 **34 行 jp 全等的副本**（`13663–13697` ↔ `13792–13826`，
  含 `13690↔13819`、`13693↔13822`）。fable-wf 已双侧逐字同改并互相登记 note，
  但若两侧被不同通道/不同裁决路径分别处理，**存在裁决后单侧入库的撕裂风险**。
- `13661 ↔ 1004`：b96 的『说不定就能救下她的』被 b97 的 1004 原样引用（原文引用时
  省了宾语、中文已补「她」）。任一侧单独润色都会断开引用关系。两侧本轮均维持原样。

裁决时这两组必须一起看，不能逐条独立定夺。

### 4. prompt 渲染格式：软锁行的标记位置会坑解析器

`b112` 的软锁行渲染成 `[b112] 12930 【软锁】: JP: …`——标记插在 id 与冒号之间。
严格按 `[bNNN] id: JP:` 写的解析器会**丢掉这一行**；fable-wf 首轮解析即因此漏了它，
靠行数对不上才发现。建议 `polish_context` 把软锁标记挪到行尾或统一格式。

### 其余（次要，登记备查）

- **`jp_tail` 的字符计数单位未定义**（Unicode 码点 vs grapheme）。三名子代理各自
  独立提了这一条。本段两通道实际都按码点计且零不符，但契约该补一句。
- **ruby 剥离规则本段基本未被行使**（多数会话的 jp 无 ruby，仅 session 5 的 13209 撞上）。
  建议在含 ruby 的批次给一个 worked example。
- **`score` 的量纲偏软**：契约说它「按改动幅度/把握程度排序」，但两者常反向
  （大改动往往把握低），一个标量同时编码两者会让下游排序语义含混。
- **prompt 标题的行数口径**：写「共 530 行」而正文数据（已剔硬锁）是 528 行。
  不影响执行，但若下游按标题数核验会误报。
- **`12890`**：opus 现行译文给拟声词加了原文没有的「」（jp 引号计数 0、zh 2）。
  照抄未动，登记为存量误报源。
- **`12530` 野菜炒め**：fable-wf 按 crd 纪要已登记的 `2077`「炒青菜」直接对齐了
  （现行「炒蔬菜」），**没走 adjudicate**。裁决时需确认这个自作主张的口径是否认可
  ——若认为「对齐已登记形」也须请裁，应把这条改回并明确口径。
- fable-wf 还点出 `rulings.md` 为空但纪要里挂着多个「请裁决/请复核」未闭环项
  （`ふむふむ` 一词三译、`まとめる` 归纳 vs 769「整理」、`12390` 原文疑似笔误
  `セクション４のあと`）——每个后续通道都要重新判一次「这是不是我该动的」，
  建议段末集中清一遍。
