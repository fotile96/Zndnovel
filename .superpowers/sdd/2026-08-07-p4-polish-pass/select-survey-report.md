# `png/select/` 烤字第四块：测绘 + 解析器改进 + 日文核验 报告（2026-08-10）

> 范围：本轮**不渲染成品 PNG**，只做测绘、解析器改进、日文来源核验。
> 起点：`docs/ops/bake-select-inventory.md`（清点）、`docs/ops/bake-decisions.md`（已定裁决）。
> 产物：`tools/derive_select.py`（新解析器）、`tools/select_layout.py`（版面测绘 + 墨迹核验）、
> `build/select_layout_spec.md`（版面规格快照，含全部证据）、`build/select_option_map.json`
> （解析器输出）、`build/select_ink_verify.json`（核验结果）、
> `tests/test_derive_select.py` + `tests/test_select_layout.py`（23 条新测试）。

## 一句话结论

**旧清点文档"73 条已有中文、零补译、73/73 命中"的结论不成立，需要撤回。**
本轮验证发现：整条"用玩家选择后到达的下一个场景的标题，反推按钮自己的文字"推导法，
即使代码调用链追踪 100% 正确执行，也有约 **46% 的概率给出错误答案**——因为"下一个
场景的标题"（叙事概括）和"按钮上刻的那句话"（玩家措辞）经常不是同一句话。这不是
某一版解析器的实现 bug，是方法论本身的结构性盲点。本轮新写的墨迹范围核验就是为了
接住这个盲点而设计的，而且确实接住了（4 组独立人工读图证实核验结果准确）。

## 一、解析器改进（`tools/derive_select.py`）

### 1.1 相对旧粗糙解析器改进了什么

旧粗糙解析器脚本本身未入库（只有输出快照 `build/select_option_map.json`，本轮已被
覆盖），据 `docs/ops/bake-select-inventory.md` 自述：只认"`doScriptScene` 字面量赋值 +
另一处 `if doScriptScene==` 分支里的 `scene_X()` 调用"这一种形态时覆盖率 34%，加上
"分支体内就地 `scene_X()` 调用"这第二种形态后到 51%。

本轮新写的 `tools/derive_select.py` 额外处理：

1. **复合条件识别并诚实拒答**（`s2s_192a/b`、`s2s_193a/b` 等谜题迷宫用
   `if (v60==1) and (v61==1) then` 联合判断两个不同 `comDlgSelectItem` 的结果，
   本解析器不做跨变量联合覆盖，报 `UNRESOLVED_COMPOUND` 并说明原因，不产出误导性猜测）。
2. **内联比较形态**（`if comDlgSelectItem(...) == K then`，无接收变量，`s2s_193c` 用此形态）。
3. **跨文件 RUN 跳转追踪**（`doScriptScene` 重定向到另一章节脚本的入口场景，
   最多 6 跳，`sel_s1s_260_sel_a` 是一个需要"本文件重定向 1 次 + 跨文件 RUN 跳转"
   两跳组合才能追到 `"サクラさん"` 的真实案例，见 `tests/test_derive_select.py::
   test_resolve_cross_file_run_jump_s1s_260_sel_a`）。
4. **修复了一个真实的 bug**：反编译代码里大量出现"`elseif` 被渲染成`else`内嵌套一个
   `if`"的等价写法（例：`lua_scripts/snr_s2_10_s.lua:2814-2886`）。修复前，这种写法会
   让第二个及之后的分支值全部误落进"共享 else"桶，与迷宫入口共享同一段错误文字
   （`sel_s2s_190_sel_b` 曾被错误地贴上 `sel_s2s_190_sel_c` 的"ナゾトキの間違い"）。
   修复后用 `_skip_if_construct` 正确展平这种"隐式 elseif"，两个按钮各自拿到正确的
   独立分支文字。这个 bug 是测试驱动开发过程中被自己的单元测试当场抓到的
   （`tests/test_derive_select.py::test_nested_if_inside_else_is_flattened_like_elseif`）。
5. **手工核实的特例**（`sel_voice1_sel_a`/`sel_voice2_sel_a`，见五之 5.1）：这两个按钮
   通过"分支内两条 `vms()` 台词拼接"这条与主推导法完全不同的规则得到答案，单独在
   `SPECIAL_CASES` 里标注，不混进主算法的置信度体系。

### 1.2 覆盖率：**从旧解析器的 51% 提升到 71.1%（81/114）**

```
resolved 81/114 buttons (71.1%)
```

（114 是本解析器覆盖的 9 个含 `comDlgSelectItem` 的 lua 文件里全部不同按钮名，
不含 `sel_map_*`/`sel_voice*` 这类走别的调用机制的资源——那些在四、五两节单独处理。）

**⚠ 但覆盖率数字本身具有误导性，见二、三节**：81 个"推出"里，经墨迹核验，只有 44 个
长度层面不矛盾，另外 37 个被证实推导错误。**"能推出日文"和"推出的日文是对的"是两件
不同的事**，这正是本轮任务交办时强调"没有任何独立证据证明推的就是图上那行字"所指的
风险，现已被实测坐实。

### 1.3 剩余 33 个仍推不出者——按原因分类（如实报告，非拍脑袋分类）

```
14  变量出现在复合条件（如 (v60==1) and (v61==1)）——谜题对错判定，非选项标题
 7  落在共享 else 分支，且该分支体内既无 scene_X() 也无 doScriptScene——通用流程，非本按钮专属
 6  选择结果变量之后未见任何 if var==K 简单判断——可能只用于复合条件或结果从未被读取
 4  分支体内既无 scene_X() 也无 doScriptScene 字面量赋值——机械解析找不到可用文本源
 2  该选项整数值在 if/elseif 链中未见任何显式分支且无 else 兜底——可能是不可达值
```

**为什么推不出**：14 条"复合条件"与部分"共享 else"都指向同一件事——`s2s_190/192/193`
一族是 CLAUDE.md 记载的"ナゾトキ 多层选择迷宫"，按钮上刻的是**谜题答案本身的候选文字**
（如"当てずっぽうで答える"之类的猜测选项），代码里只有"这个答案对不对"的布尔判断，
从未把候选文字本身写成字符串字面量——这批文字**只存在于图里**，任何机械解析都无法
从 lua 恢复，需要逐张读图（工作量与 `docs/ops/bake-select-inventory.md` 原判断一致，
本轮解析器改进没有、也不可能消灭这一类）。

## 二、墨迹范围核验（`tools/select_layout.py`）——本轮最有价值的部分

### 2.1 判据与阈值

- **判据**：预测宽度 `= n_chars × 16.59px`（校准常数，见 2.2）与实测墨迹宽度的相对偏差
  `|measured-predicted|/predicted`，超过 **30%** 判定 `mismatch`。
- **阈值来源**：6 组独立校准样本彼此间的 px/字比值偏差不超过 3%（16.2–17.0px 紧窄区间），
  证明"用固定常数预测不同长度文本"的自然噪声很小；30% 容差远宽于这个噪声（不会把正确
  答案误判为 mismatch），同时稳定捕获实测到的真实错误（幅度普遍在 30%–298%，见 2.4 表）。

### 2.2 校准集：6 组本轮独立人工核对（放大截图直接读像素），不沿用旧结论

| 按钮 | 校准文本 | 墨迹宽度(px) | px/字 |
|---|---|---:|---:|
| `sel_s1s_35_sel_a` | 約束を思い出せない（9字） | 149 | 16.56 |
| `sel_s1s_35_sel_b` | 約束をしている（7字） | 116 | 16.57 |
| `sel_s1s_35_sel_c` | 約束をしていない（8字） | 132 | 16.50 |
| `sel_s5s_350_sel_b` | がんばってみる（7字） | 115 | 16.43 |
| `sel_s5s_350_sel_a` | 無理はしない（6字，真实文字，见下） | 99 | 16.50 |
| `sel_s5s_80_sel_c` | 雪が降る（4字，真实文字，见下） | 66 | 17.00 |

均值 **16.59px/字**。后两组的"推导链原答案"都是错的（下表展开）——特意选它们做校准，
是因为它们提供了"推导法失败的真实反例 + 正确答案"这一对最有诊断价值的数据。

### 2.3 核验结果：**44 match / 37 mismatch / 0 no-ink / 0 no-image（46% 不匹配率）**

对新解析器产出的全部 81 个候选跑核验（`uv run python tools/select_layout.py
--candidates build/select_option_map.json`）。

| `sel_s5s_80_sel_c` | 旧粗糙解析器给的"雪が降るって言うウワサ"（本轮解析器已改判不可推导） | — | **"雪が降る"** | 旧解析器答案是"猜对了前 4 字、编造了后 7 字"的典型幻觉产物 |

而该文档同一节明确写"我只肉眼验了 1 条"——**这条被举例的"确认样本"本身就是错的**，
直接证伪了"73/73 命中"的可信度。旧解析器脚本未入库，无法逐条重新核对全部 73 条，
但 4/4 独立读图 100% 复现"推导法有结构性假阳性"这一结论，足以判定该方法论层面的
风险是普遍存在、不是个别偶发。

### 2.5 全部 37 条不匹配清单

见 `build/select_layout_spec.md` §5.3（含按钮名/推导文本/实测像素/预测像素/偏差比例）
与 `build/select_ink_verify.json`（结构化数据）。摘要按章节分布：

```

```

集中在 s2s/s3s——与"ナゾトキ多层迷宫""ウワサ支线多选"这两处 CLAUDE.md 记载的复杂
分支密度最高的章节吻合。

### 2.6 这个核验能证明什么、不能证明什么（诚实边界）

- **能**：预测宽度与实测宽度差异悬殊时，几乎确定是错的（4/4 独立验证支持）。
- **不能**：两个字数相同、语义不同的短语，墨迹核验无法区分——"match" 不等于"证实正确"，
  只是"长度层面不矛盾"。44 条 match 里，只有 6 条（校准集本身）经过了独立像素级复核，
  其余 38 条仍需人工逐条读图才能真正定稿。

## 三、版面测绘结论

完整测绘与证据见 `build/select_layout_spec.md`（本轮生成，含全部测量方法）。要点：

- **底色形态**：**平色 + 双层同心边框环 + 四角半透明装饰缺口**，与 `png/scene/` 同型
  （不是 `png/plot/` 那种需要逐格动态测墨迹高度的照片底）。`off` 内部填充
  `(0,0,0,129)`、`on` 内部填充 `(235,164,128,255)`，均已实测确认为纯色（134 个按钮的
  边框/装饰区随机抽样比对，字节级一致，仅 3 例出现 ±1/255 的抗锯齿噪声）。
- **原判断"左侧小方框图标"是误读**：实测那是一个跨全部按钮共享的固定透明装饰缺口
  （`x∈[5,10], y∈[5,6]`，off/on 两态都验证过），不承载任何按钮专属信息。
- **文字对齐方式**：**水平垂直双向居中**，不是左对齐（134 个按钮墨迹中点统计：
  中位数 x=124.5，标准差仅 0.72px）——这一条与清点文档"排版方案待定"的开放问题
  直接相关，现已有测绘证据支持"这批按钮比 `scene/` 更简单，也是固定矩形居中覆盖，
  不需要 `plot/` 的逐格色带机制"。
- **可用文字区**：建议 `TEXT_BOX` 中心 `(124.5, 12.5)`，可用宽度约 220px（比实测墨迹
  最大跨度 `[35,209]` 留出余量）。
- **中文试排**：本轮**未做**（第五节展开原因——判据本身尚不稳定，日文源仍有 46% 错误率，
  在源文本定稿前排版试排没有意义，遵循"这一步没做之前不要估工期"的既有纪律）。
