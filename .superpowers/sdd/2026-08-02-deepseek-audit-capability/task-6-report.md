## 3. 试跑中发现的三个实质问题（都影响全量跑的可信度，建议先决定要不要修）

### 3.1 `prewire_ids` 不认区间写法 `id 17050–17121`（阻断级，会系统性制造「无法判断」）

`ID_RE` 的字符类是 `[0-9０-９、,， \t]`，不含破折号。实测：

```
prewire_ids({'body': '- id 17050–17121 等；……'}) -> [17050]
```

——**只拿到区间的第一个 id**，模型于是拿着 1 行去核 19 行的整族承诺，只能判
「无法判断」（§4 案例 A 正是此情形）。

全语料 `grep -oE "id [0-9]+[–—−-][0-9]+"` → **50 处**，分布在 crd/s1f/s1s/s2s/s3s
五个文件。按试跑 17 条硬承诺出 2 条「无法判断」的比例，全量跑里这类会是「无法
判断」的主要来源之一，且是**工具侧的缺陷、不是语料的问题**。

### 3.2 `verify_promise` 不给模型看提案正文（设计缺口）

送给模型的 user 消息只有 `kind` + `quote` + 出处 + 相关行：

```python
user = (f"【承诺】{promise.get('kind')}：{promise.get('quote')}\n"
        f"【出处】…\n【相关行】\n{ctx}")
```

承诺内容住在正文里的（表格、清单、逐条对照）一律核不了。§4 案例 A 里模型说
「承诺所依据的『表内译法』表未随材料给出」——**这句抱怨是准确的**：那张 19 行的
译法表就在提案正文里，但没被传进去。模型的「无法判断」在这里是**正确且诚实的**。

### 3.3 `evidence_ids` 静默丢弃字符串型 id（与抽取阶段口径不一致）

```python
"evidence_ids": [i for i in (data.get("evidence_ids") or []) if isinstance(i, int)],
```

而抽取阶段的 `_clean_model_ids` 是接受 `"007"` 这类纯数字字符串的。试跑 15 条
「已履行」里有 **3 条**（crd b10 #9「模糊」、b10 #10「《汉堡》」、b10 #2「進め方」）
`evidence_ids == []` 却在 `reason` 里明确点了行号，报告因此印出「依据行：（无）」。
sidecar 存的是过滤后的值，**我无法从留痕反证模型当时给的是字符串**，所以这条是
**代码层确凿的口径不一致 + 对那 3 条的合理但未证实的解释**，不是已证实的因果。

### 4.1 「无法判断」案例 A —— crd b10 #2

- **提案**：crd · b10 · #2 ·「系统教程伪说话人标签族（19 个）——建议整族一次定死」
- **承诺（模型概括）**：本批伪说话人标签已按表内译法统一落笔
- **承诺原话**：`本批落笔如下`（后接一张 19 行的「原文 | 本批译法 | 备注」表）
- **依据行**：`（无）`；`promise.ids = [17050]`，`ids_source = model`，`prewire_ids = [17050]`
- **实际材料只有一行**：
  - id 17050（crd）｜ jp `【≦＊＊＊≧】■セカンドノベルの進め方` ｜ zh `【≦＊＊＊≧】■第二物语的玩法`
- **模型理由**：「该行译文确实保留了【≦＊＊＊≧】标签，但承诺所依据的『表内译法』表未随材料给出，且仅凭单行无法核对 19 个标签的『整族统一落笔』，故无法核实是否按表落实。」

**我的独立复算：同意「无法判断」，而且模型给的两条理由都经得起查——但根因在工具，不在语料。**

1. 「仅有单行」属实，且**是工具造成的**：提案正文写的是 `id 17050–17121 等`，我
   实跑 `prewire_ids` 确认它只截到 `[17050]`（§3.1）。该族真实存在的行远不止一行，
   我抽查了 17051 / 17118 / 17121，译文均原样保留了 `【≦＊＊＊≧】`。
2. 「表未随材料给出」属实：我读了 `verify_promise` 的 user 拼装（§3.2），提案正文
   确实不在其中。模型不是在推诿。

**结论**：这条「无法判断」是**正确判定 + 工具缺陷的叠加**。它没有把不确定硬判成
「已履行」，符合 spec §4.4；但它也说明**全量跑里这类「无法判断」会被工具缺陷放大**，
读报告时不能当成「语料本身证据不足」。

### 4.2 「无法判断」案例 B —— crd b10 #2（同一提案的另一条承诺）

- **承诺（模型概括）**：【≦＊＊＊≧】原样保留不译
- **承诺原话**：`【≦＊＊＊≧】原样`
- **依据行**：`（无）`；`promise.ids = []` → 走工具兜底，`used_tools = True`
- **模型理由**：**`（模型未给出可解析的判定，或输出不是合法 JSON）`** —— 即兜底文案，不是模型自己的话
- **CoT 末尾**：仍停在「让我并行搜索几个关键词。」，并已明确写下「crd 章节中有：id 17050-17054, 17118-17121：这些是【≦＊＊＊≧】标签，译文保留了【≦＊＊＊≧】原样」，但在纠结「承诺说 19 个、我只搜到 9 个」

**我的独立复算：判定结果（无法判断）可以接受，但这条的「无法判断」与案例 A 是
两种完全不同的东西，报告没有把它们区分开——这是我对实现的一条异议。**

- 案例 A 是「材料不足以判定」。本条是**模型压根没交出可解析的判定**：它调了工具、
  没触发任何一条机械闸（`stopped_reason=finished`、`tool_errors=0`、`tool_calls` 非空），
  最后一轮却没吐出合法 JSON，于是掉进 `VALID_VERDICTS` 兜底。
- 两者在报告里长得一模一样（都是 `[无法判断]` + 依据行「（无）」），读者无从分辨
  「证据不够」和「模型没答」。**建议 reason 里显式区分**，否则报告顶部的「无法
  判断占比」这项可信度指标会把两类问题混成一个数。
- 顺带：模型自己在 CoT 里其实已经查到了答案（9 行全部原样保留）。我独立核了
  17050/17051/17118/17121，`【≦＊＊＊≧】` 均原样保留。**这条实质上是「已履行」被
  流程弄丢了**，不是证据不足。CoT 不得作为判定依据（spec §5.3），所以我**不主张**
  把它改判成「已履行」——但这说明兜底掉的那条判定是有代价的。
