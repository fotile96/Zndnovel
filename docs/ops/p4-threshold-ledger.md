# P4 阈值调整台账

`config/polish.yaml` 的阈值集中在一处（spec §9），任何调整在这里留一条记录。
体例沿用 P3 runbook §四「判定记录」：**改了什么 / 为什么 / 影响哪些在产 SEG / 全量测试结果**。

约束提醒（runbook §十二）：SEG-1 实测后的阈值调整**只认抽检推翻率与裁决实感**；
spec §9 明写「任何阈值调整不得以自动入库率为优化目标」。方向性判据——把闸门**开大**
（更多人工介入、更少自动放行）不受该条约束，把闸门**关小**则必须有推翻率数据支撑。

---

## T1 — `K`: 150 → 500（2026-08-07）

**改了什么。** `config/polish.yaml` 的 `K`（每 SEG 请裁配额总额，多通道共享，含抽检占用）
由 `150` 上调为 `500`。其余阈值一律未动。

**为什么。** SEG-1（seg1-s2）是 P4 润色 pass 首次正式生产启动，且**两条通道的准入小考都
未通过**（`channel_state.json` 两条均 `autoclear:false`，原因见 handoff「准入小考」节：
正常润色行为会误伤既有人工裁决），因此本 SEG 全部候选一律走人工裁决队列、没有任何自动
清关捷径。此前的 `K=150` 是按「有免检通道分流掉大头、人只看残余」的常态设计的，在
「全量人裁」这个形态下会把段末队列**静默压缩成抽样**——首个 SEG 恰恰是最需要看全、最需要
积累裁决实感的一段。用户裁定：本段宁可多花人力，先拓宽队列容量，段末一次裁完。

取值依据（实测外推，非拍脑袋）：session 1 的 568 行经两条通道产出 1132 条候选，去重后
**裁决队列 72 个 id**（占该会话行数 12.7%）。SEG-1 四个会话合计 1996 行，按同一比率外推
约 **253 个 id**。取 `500` ≈ 外推值的 2 倍、全段行数的 25%，给批次间改动率方差留足余量；
同时不取「大到形同废除」的值——若队列**仍**超过 500，那是真信号（`triage.json` 的
`meta.sampled_dropped` / `forced_soft_over_budget` 会显式播报），应当被看见而不是被吸收掉。

**影响哪些在产 SEG。** `K` 是**全局键，没有 per-SEG override，也没有 CLI 覆盖**
（`polish_triage.py` 只接受 `--seg`/`--repo`）。当前在产的只有 seg1-s2，故实际影响面仅此
一段；但**该值不改回或不改成 per-SEG，会一路影响 SEG-2..N**。

⚠ **未决项（SEG-1 段末复盘时必须裁定）**：三选一——(a) 调回 150；(b) 依 SEG-1 的实际裁决
实感定一个新的常态值；(c) 给 `polish_triage.py` 加 per-SEG override（`K_by_seg`），让
「首个 SEG / 无免检通道的 SEG 放宽」成为机制而不是一次性手改。在此之前 `K=500` 是**临时
状态**，不是新常态。

**全量测试结果。** 见本条落地 commit——改动仅一个 YAML 标量，不触碰任何代码路径；
`uv run pytest -q` 应仍全绿（基线 780 passed）。

**后续实测（2026-08-07 段末回填）。** SEG-1 全段实际裁决队列 **233 个 id**，与外推的 253
基本吻合；`triage.json` 的 `sampled_dropped=0`、`forced_soft_over_budget=false`，队列未被
压缩。若沿用 `K=150`，会有 **83 个 id 被静默截断**。另见 T2——K 拓宽还顺带把放大扫描的
主要收益提前兑现了。

## T2 — SEG-1 放弃放大扫描轮（2026-08-07）

**改了什么。** 没有改配置（`amplify_rounds` 仍为 1）。这里记的是**用掉配额的方式**：
SEG-1 的那一轮放大扫描**主动不跑**，`raw/amplify/` 与 `candidates.amplify.jsonl` 在本 SEG
永不存在。`polish_amplify.py --digest` 已跑（纪要有价值，留档），`--scan-prompt` 生成的
`work/ctx/p4s1-amp.md` 未派发给任何通道。

⚠ **`plan.json` 里留下了一条 `{"session":5, "channel":"amplify", batches:36–62}` 记录**——
那是 `--scan-prompt` 渲染时写的，如实记录"这份 prompt 被渲染过、哈希是多少"，**不代表它
被执行过**。判断放大轮是否真的跑过，看 `raw/amplify/` 目录与 `candidates.amplify.jsonl`
是否存在，不要看 `plan.json`。保留该记录是为了：万一将来决定补跑，倒查链需要这个哈希。

**为什么。** scan prompt 自述的主要靶子是**桶 3（落选候选）**——"曾产生真实改动、却因人工
裁决配额有限而从未被人看过"的行。而 T1 把 K 提到 500 之后，**本 SEG 桶 3 = 0**（分流结果
桶1 3714 / 桶2 269 / 桶0 = 桶3 = 0），一条都没落选。**放大轮的主要收益已经被 K 拓宽提前
兑现掉了。** 剩下的次要靶子（桶 1 里可能被通道武断判成"零改动"的行）要付出两条通道各重扫
全段 27 批（各约 1992 行）的代价——比整个生产阶段还大——且 `amplify` 通道恒不自动清关，
产物只能进人裁，会再生出一批待裁队列。

用户裁定：本段不跑；**将来在整个 P4 跑完之后，如有必要另行安排一个 pass，以 P4 最终落盘
的文本作为新 pass 的待润色输入**。这比在单个 SEG 内部做放大更合理——那时全部 SEG 的裁决
尺度已经统一，且输入是终稿而非中间态。

**影响哪些在产 SEG。** 仅 seg1-s2。**这不构成后续 SEG 的先例**：桶 3 是否为空取决于该 SEG
的 K 与候选量，后续 SEG 若出现非空桶 3，放大轮的主要收益就回来了，应照跑。判据写死一句：
**看 `triage.json` 的桶 3 计数，不是看"上个 SEG 跑没跑"。**

**全量测试结果。** 未触碰代码与配置，780 passed 不受影响。
