# 长对话多批生产模式设计（main 车道）

> 起草 2026-08-03，基于 b63–67 五批受控实验的实测数据。
> **状态：定稿**。b63–67 五批 + b68–72 续跑（同一对话推至 10 批 / 585 行）数据均已回填。
> 上游观察：`docs/superpowers/specs/2026-08-03-extra-lane-collapse-design.md` §7.1。

---

## 0. 目标与非目标

**目标**：把 main 车道正文批的生产，从「每批一个全新 subagent 会话、每批重投一份完整 `context.md`」改为「一条长对话连做 N 批、固定材料只投一次」，在不牺牲规则遵守的前提下大幅降低投喂量。

**非目标**：

- ✗ 改 `data/batches.jsonl`（冻结）
- ✗ 改 `check_batch` / `detect_collapse` / `append_forward` 的逐批语义（校验仍逐批做）
- ✗ 改 `build_context` 的产出（ctx 照常逐批生成入档，只是不再整份投喂）
- ✗ 跨 glossary 版本变更的长对话（见 §4.3）

---

## 1. 为什么值得做：每批固定开销的实测构成

`context.md` 五节的体积构成（opus 车道实测）：

| 节 | 体积 | 性质 |
|---|---|---|
| 一、冻结骨架（196 张卡） | 8442 字符 | **恒定** |
| 二、前缀正文 | 18K–50K | 随进度增长 |
| 三、锚点行 | **9439 字符** | **b63–67 逐字完全相同**（全库锚点全量内嵌，不随批次变） |
| 四、术语+风格+7 份口调表 | 26864 字符 | **近乎恒定** |
| 五、本批任务 | 41–1810 | 随批变 |

**第一、三、四节合计约 44.7K 字符，每批原样重投一遍。** 173 批即约 7.7MB 的重复投递。

第二节虽然增长，但在长对话里模型**已经亲手译过**前面几批，无需重投。

### 1.1 实测投喂量（b63–67 五批）

| 模式 | 投喂量 |
|---|---|
| 逐批（现状） | **594KB** |
| 长对话 | **131KB**（b63 全量 115KB + 后 4 批 `source.jsonl` 合计 16KB） |
| **降低** | **78%** |

耗时 13 分钟 / 240 行 ≈ 18 行/分钟，**快于逐批模式**（省在不重复读 115KB 工作台）。

## 2. 实验设计与混淆变量的消除（方法论留档）

对照组 A = **b63–67 的生产译文本身**（opus 逐批、glossary v8）。用生产产物而非重跑作对照，因为它是真实出货的артefact。

采用它的前提是 **v8→v9 的差异对这 5 批惰性**，已逐项实测：

| 检查 | 结果 |
|---|---|
| 重生 ctx 与生产版差异 | 22 行，**全部集中在 style.md 节** |
| v9 新增职名例外表（`教頭`/`顧問`/`校長`） | 在 b63–67 原文中 **0 次出现** |
| v9 `active.json` 新增 4 词（射的/水風船/ボールペン/鉛筆） | **0 次出现** |
| 当日新落的 4 条 patches | 未落入 b63 前缀窗口 |
| 各批第三节（锚点行） | **逐字完全相同**，长对话带一次即可 |

> 最后一条是实验成立的前提。若未验证就开跑，Mode B 在 b64–67 会丢失锚点定译，产生**与对话结构无关的假失败**，进而得出「长对话不合规」的错误结论——而真因是实验设计漏了材料。

### 2.1 已发生的设计缺陷（如实记录）

实验车道由生产车道整份拷贝而来，其 `data/forward.jsonl` **含 b63–95 的成品译文**，而译者指令明确鼓励译者 grep 该文件查既有译法——**等于把答案留在了考场里**。

执行者在为 b63 检索译法时撞见约 7 行生产译文后主动交代、点名受污染的具体行（11314/11348 最终文字与生产版几乎一致）、备份原件并把 `forward.jsonl` 截至 batch ≤62，此后 4 批检索干净。

**污染面的独立佐证**：b63 与生产版逐字相同率 33%，与干净的 b64–67（29–37%）无差别。若污染显著，b63 应明显偏高——它没有。

**后续实验必须先截断车道副本的 `forward.jsonl` 至待译批次之前。**

## 3. 实测结果（b63–67）

### 3.1 客观指标：无总量级合规崩坏

| batch | 行数 | check hard | check warn | collapse |
|---|---|---|---|---|
| 63 / 64 / 65 / 66 / 67 | 240 | **0** | **0**（初稿 2 处 W3，短行阈值余量问题，已修） | **0** |

与生产译文 **76/240 行（31%）逐字相同**——一次完全独立的重译能有三成逐字撞上，说明骨架/术语/口调/锚点这套约束确实在承重。

### 3.2 失效机制（本实验最有价值的产出）

执行者自陈 **batch 66 是拐点**，并给出可检验的实例：处理 `落ちる` 时**先落笔写了「掉下去」，事后才想起** yuichi 口调表 §6 正是这么规定——**顺序反了**。

复算结果：生产版与实验版**均为「掉下去」，无实际错误**。故这不是事故，是**近失事件**（near miss）——比事故更值得记，因为事故会自己暴露，近失不会。

**退化的选择性**（本 spec 的核心发现）：

| 退化最快 | 不退化 |
|---|---|
| `style.md` 润色四条边界、补『』三条口径、口调表 §6 特殊注意 | `active.json` 术语表 |
| **低频触发 + 无机械兜底** | **短、且有 W2 机械兜底** |

> 规律：**有机械闸兜底的规则不会因遗忘而失效，因为遗忘会被闸抓住；没兜底的规则只能靠记忆，而记忆会衰减。**

### 3.3 一句话概括真实代价

> **长对话把「与表一致」换成了「与自己一致」。**

跨批一致性**变好**（b63 定的措辞到 b66 零成本复用；逐批模式只能靠 grep 撞运气）。代价是规则遵守从「查表」滑向「自洽」——本次两者未冲突，**但一旦冲突，自洽会赢**。

## 4. 方案：部分重投

### 4.1 分档处理

| 材料 | 体积 | 处理 |
|---|---|---|
| 一、冻结骨架 | 8442 | **只投一次** |
| 三、锚点行 | 9439 | **只投一次**（已验各批逐字相同） |
| 四之 `voices/`（7 份） | **21887（占第四节 81%）** | **只投一次** |
| 四之 `style.md` | 4376 | **每批重投** |
| 四之 `active.json` | 601 | 每批重投（有 W2 兜底，成本可忽略故一并投） |
| 五、本批任务 / `source.jsonl` | 随批 | 每批投 |

**每批仅需重投约 5KB 即可补上退化最快的部分**，而 81% 的固定开销（口调表）仍只投一次。

### 4.2 逐批校验不变

`check_batch` / `detect_collapse` / `append_forward` 仍逐批执行，hard 修到 0 才入库。**校验链完全不感知对话结构**。

### 4.3 硬约束：不得跨 glossary 版本

长对话中规则书只投一次；若中途 glossary 升版（本项目段末裁决会跳版），对话内的规则书即过期。**一条长对话不得跨越 glossary 版本变更**——该约束天然与段边界对齐。

### 4.4 复现性凭证不变

`build_context` 照常逐批生成 `context.md` / `source.jsonl` / `manifest.json` 并入档，只是第 2..N 批不再整份投喂。`manifest.json` 的 `ctx_sha`/`glossary_v`/骨架与锚点哈希照常留痕，canary 与审计链不受影响。

### 4.5 爆炸半径

会话中途失败时，已完成批次早已 `append_forward` 入线，重开一条从断点续即可。

## 5. 续跑实验（b68–72）：上一轮的结论被推翻

同一条对话续推至 **10 批 / 585 行**。工装结果：b68–72 五批 **hard/warn/collapse 全 0，初稿即零返工**。

**但这个数字是假的好看**——见 §5.2。

### 5.1 退化的层次被修正了

上一轮判断「退化的是低频触发+无机械兜底的**规则记忆**」。续跑后执行者**自行推翻**：

> 规则记忆本身**没有**进一步退化，甚至更稳（前文积累让双层人名、控制码、speakers 映射的处理更笃定）。
> **真正在退化的是「这句需要外部核对」的风险识别。**

证据是一次**机械自查**（非内省）：对 b68–72 每个 id，在 ledger 里找 **jp 逐字相同**且已入线的兄弟行比对 zh —— **16 组复现句，3 组不一致**。

执行者对失效模式的归纳：

> **复现句在「看起来不值得查的句子」里密度最高，而那恰恰是我最不会去查的地方。**

全库实测支持这个判断（见 §5.4）：>25 字的复现句族**零违例**，≤10 字的违例率最高。

### 5.2 上一轮的报告是在已有未检出缺陷的情况下作出的

续跑的机械自查还查出：**batch 67（上一轮）已存在一组同样的失配**——3227 与已入线的 1926 jp 逐字相同，被重译成另一句。

也就是说，上一轮报告「b63–67 没有进一步退化」时，**手上已有一条实质缺陷未被检测到**——因为当时**只做了主观内省，没做机械自查**。

> 这条修正比续跑的任何新发现都重要，并再次印证本项目的既有教训：**自陈需要被复算，而复算必须是机械的。**

### 5.3 与逐批模式的对照（关键）

对 5 组复现句失配逐组比对生产版（逐批模式）：

| 复现句族 | 生产（逐批） | 实验（长对话） |
|---|---|---|
| 2976→3283 | ✅ 一致 | ❌ 失配 |
| 8612→11556 | ✅ 一致 | ❌ 失配 |
| 1926→3227 | ✅ 一致 | ❌ 失配 |
| 8629→11650 | ❌ 失配 | ❌ 失配 |
| 8629→11708 | ❌ 失配 | ❌ 失配 |

**3 组是长对话独有的退化**（逐批做对了）；**2 组两种模式都错**——说明「复现句族」这条规则本身有系统性漏网，非长对话特有。

### 5.4 附带发现：工装心智模型错误 → 直接造成 2 组失配

执行者对 `check_batch` W3 的判据有两处错误认知，实测判据为：

```python
_max_line_width(zh) > max(10, _max_line_width(jp) * 1.15)
```

即 **(a) 有 10 的地板**、**(b) 宽度按整行算、含 `【说话人】「」` 外壳**（CJK 按宽 2）。实测两条被"收紧"的复现句原本根本不会触发 W3（阈值 25.30 / 32.20，而写自然译文只有 24 / 26）。

**它为一个不存在的 W3 风险，主动牺牲了两条复现句的一致性。**

由此得出的一般教训（已写进车道 notes）：

> **工装绿灯与译文合规是两回事，而人会不自觉地把绿灯当成合规证明。**

这也解释了 §5 开头「初稿即 warn=0」为何是假的好看：**现有闸门覆盖不到的规则，绿灯不提供任何保证。**

### 5.5 另一类缺陷：手记里写进了一条并不存在的规则

执行者自查发现，上一轮它把「彩野的 `ごめんね` 译作『对不起哦』」**过度解读成「该词组为彩野专属、他人不得使用」**，并作为先例写进了 `notes/crd.md`。译文本身无害，但**下游会把它当既定规则沿用**。已正式撤回。

> 这类缺陷是**手记里写进了虚构的承诺**，与「承诺未被履行」相反。现有的手记「承诺-履行」审计器**审不到这一类**——它只核对承诺是否被执行，不核对承诺本身是否成立。记为审计能力的已知缺口。

### 5.6 批次上限：暂定 10 批，并附条件

10 批 / 585 行未出现总量级崩坏（hard/warn/collapse 全 0），速度稳定在约 18 行/分钟。但既然已确认存在长对话独有的复现句退化，**上限不应由「还没崩」来定**，而应由 §6 的补偿措施是否到位来定。

**暂定：单条对话不超过 10 批，且必须满足 §4.1 的部分重投与 §6 的 W4 机械闸。** 后续可在 W4 上线后重测更长的对话。

## 6. 配套机械闸：W4 复现句族一致性

§5.3 证明「复现句族内逐字一致」在两种模式下都有漏网，而它是 `style.md` 里**唯一一条被明写为「不放宽的边界」却无机器兜底的规则**。

**全库噪声实测**（`ledger.jsonl` 的 jp × 车道 `forward`+`patches` 的 zh）：

| 指标 | 值 |
|---|---|
| jp 逐字相同且均已译的族 | **340 组 / 1113 行** |
| 其中 zh 不一致 | **19 组（5%）** |
| ≤10 字 | 8/100（8%） |
| 11–25 字 | 11/165（6%） |
| **>25 字** | **0/75（0%）** |

5% 报警率属顾问级理想量级（对比：C3 重做前 87% 命中里 93% 是误报）。长度分布独立支持 §5.1 的归纳——**长句零违例，短句违例率最高**。

**判据**：对本批每行，在全库找 jp 逐字相同且已有译文的兄弟行；任一兄弟 zh 不同即报，消息须写明兄弟 id 与其 zh。归 **warn 不归 hard**（存在语境导致的正当分歧，且本项目已吃过谓词过严淹没真信号的亏）。

**不加长度阈值**——「>25 字零违例」是当下数据的结论，不是应写进代码的规则。

> W4 对**逐批模式同样有价值**（§5.3 中 2 组失配来自逐批生产），故不依赖长对话方案落地。
