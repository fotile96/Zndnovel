# P3 方针设计：opus 侦察全量 + 检查点裁决 + 并行开发

> 承 P2 试点（`docs/superpowers/reports/2026-08-01-p2-pilot-report.md`，35 批全部过审）。
> 本 spec 是**方针级**设计：定角色、节奏、并行安全、开发优先级与 API 路线里程碑；
> 各执行单元的具体步骤由后续实施计划（writing-plans）展开。
> 定稿日 2026-08-02，与用户逐项确认后落档。

---

## 0. 决策来源与既定事实

用户人工评审 P2 全部输出后的三条观察（本 spec 的输入约束）：

1. **压缩窗口机制的影响可接受**——不再作为 P3 的重点验证对象。
2. **fable 译文文风明显更好**（opus 有翻译腔）；**opus 的 notes 质量极高**（216 条提案多切中要害），fable 手记松散。成本：opus 35 批 ≈ 10% 周额度（≈0.29%/批），fable 1 批 ≈ 1% 周额度（全量 ≈ 3.4 周满额度）。
3. 接下来开发会话与生产会话**并行推进**，同一订阅额度供两者共用；外部 API 路线适合优先推进开发。

由此，P2 悬置的「v1 译者选型」以**角色分工**方式解决，不再做额外对照实验。

## 1. 角色与可见性

- **opus = 侦察车道**（沿用 `pilot/lanes/opus`，从 batch 36 续跑余下 304 批）。产物三件套：
  译文草稿（证据 + 应急垫底）、notes（裁决供料）、机检记录。**草稿不是成品**。
- **fable = 成品车道**（P4，另立 spec）：等 opus 全量 + 最终裁决出 v8 后启动。
- **可见性政策（「洞察过河、文风不过河」）**：
  - fable 可见：最高版 glossary、扩容后 anchors、style、**经用户筛选的逐批 `tr_note`**。
  - fable **永久不可见 opus 译文草稿**——上下文装配时物理排除 `pilot/lanes/opus/`，加断言。
  - notes 过河的**唯一通道**＝检查点裁决会话中用户人工筛选（P2 §10 实测 notes 自述理由错误率 3/13，未经筛选不得过河）。批次局部、全局机制载不动的提醒（双关、说话人身份未明等）筛后写成对应批的 `tr_note` 注入上下文（该机制已存在，P2 冻结卡 128 的 tr_note 被译者正确执行过）。

**排除项**（发散阶段已判定为陷阱，留档防止回潮）：

- ✗ opus「裸手记模式」（只产 notes 不产译文）——notes 可信度来自「真的做了翻译」，且丢译文使锚点/剧透/崩溃三套机检失去对象。
- ✗ 按叙事重要性把关键章派给 opus 产文——与实测反向，opus 优势在观察不在产文。
- ✗ 双模型同批对撞出「价差」——额度翻倍，P2 已回答该回答的。
- ✗ raw notes 实时喂 fable——错误理由随之过河。

## 2. 节奏：检查段 + 段末小裁决

- 304 批按章切 **约 8 个检查段**（切分表在实施计划阶段从 `analysis/dag_all.txt` 与 `data/batches.jsonl` 定；e2s 单边对话、s7f 递卡段天然落在时间轴末段，符合「上下文最完整时再翻」的既有要求）。
- **段完成 = 机检全绿 + 用户抽读关键场 + git tag**（命名规约如 `prod-opus-s3-done`）。
- **段末小裁决**（替代「期末一次大修」，用户裁决：少量多次对人更友好，不担心术语基准切换弄脏证据链，留痕即可）：
  1. **纯章内项**（双关、孤例）当场裁决；
  2. **饱和度闸门**：新工具从 ledger 计算词族「全书出现次数中已被译过批次覆盖的比例」，**≥80% 才允许裁决**；未饱和词族只做词族聚类归档，滚存到后续检查点。这是 P2「不在 10% 证据面上锁死全书术语」教训的机械化。
  3. 每次裁决量 ≈ 一章提案 − 未饱和滚存（几十条级）。
- 裁决产出 glossary 小版本 + 召回令；回改走 patches（2378 通路已验证）；**段内版本锁死**，切换只在段边界；manifest 记录每批所用版本号。
- 最后一段的裁决即「期末大修」的残余（只剩尾部才饱和的词族），收尾定版 **v8**。
- **术语登记纪律**（v7 收尾确立，强制沿用）：`active.json` 每新增一条，先跑「对已入线译文的 W2 命中率」再定稿；值＝可字面校验的核心串，不必等于完整定译。

## 3. 并行安全：生产钉死工具链

- **生产会话从钉死的 worktree 执行 `tools/`**（如 `../Zndnovel-prod`，checkout 在 tag `prod-run-v1`）；车道数据仍在主仓（`ZND_DATA` 指向），worktree 只提供代码。dev 在 main 上自由改。
- **工具升级只在段边界**，闸门＝**陷阱批回验**：用新工具重验最近已过审段的全部校验，判定与当时留痕 diff 一致才滚动 tag。`canary.py` 脚本化。
- manifest 追记 `tools_tag` 字段，每段的工具版本可追溯。
- **额度软政策**（可随时调整，不设硬机制）：生产涓滴默认在跑、目标 ≤50%/周；dev 按需；留 ~15% 缓冲。进度按**段**而非按批盯：每周 1–2 段 + dev 余量。
- **生产会话开场自检**写进段间交接文档：worktree tag、`lane_setup --verify`、额度余量三件事。

## 4. 校验下沉（用户原则）

> 可字面化的硬规则留在校验器；难以形式化的语法/语感要求不再追求校验器化——
> ①译者 prompt 加一两行提醒（几十 token 级成本）；②检查点人工抽读兜底。
> 语法层面难以刻画的小出入对实际阅读影响有限，不值得高成本机械围堵。

P2 的 13 条缺陷据此重定级：

| 级别 | 缺陷 | 处置 |
|---|---|---|
| 顺手降噪 | F12（`・` 入假名正则）、F9（C1 白名单）、F4（C3 常量加 CLI 开关） | 一行级修理，点火后随 dev 会话完成，段边界经 canary 上生产 |
| 段边界修 | F7（ledger 无行序字段） | 唯一影响译者上下文本身的缺陷；首个段边界升级 |
| 不再投入 | F8/F11（W2 词性/指称盲区）、W2 鲁棒化 | 用登记纪律（§2）+ prompt 提醒 + 人工抽读替代 |
| 持续投入 | F10（母题句族锚点覆盖不全） | 这是骨架/裁决工作而非校验器工作：机器横扫（母题族、引号内术语聚类）每段跑一次，与 notes 双轨供料给段末裁决 |

新增 dev 工具三件：**饱和度计算器**、**`canary.py`**、**提案词族预聚类 helper**。

## 5. API 路线：里程碑 1 = 回译质检器（「彩野测试」）

- **薄管道层**：API client、`.env` key 管理（绝不入库）、按 token 计费台账。
- **第一个消费者＝彩野测试**：便宜外部模型（gemini/deepseek）扮演「只靠梗概续听的人」——只喂压缩前缀 + 该段译文（**不给原文、不给全文**），回答剧情理解题（谁在等谁、这封信谁写的、这个称呼为何变了）。答错处＝译文或压缩丢了信息，且丢的恰是真实玩家会丢的信息。每检查段跑一遍当额外验收，**零订阅额度消耗**。
- 与本作机制同构（15 分钟记忆 + あらすじ压缩），题库可直接取材游戏内卡片谜题的关键词关系。
- 同一管道未来可升级为第三翻译车道（fable 全量额度过贵时的 plan B）——**现在不建**，只保证管道分层上翻译适配是「换 prompt」级扩展。

## 6. 排期草图

| 时段 | 生产轨 | 开发轨 |
|---|---|---|
| 本周 | 点火三件套：段切分表、worktree 钉死、首段 gen_plan → **开跑** | 饱和度计算器、canary.py |
| 1–3 周 | 检查段滚动，段末裁决会话 | 降噪修理上生产（段边界）、API 管道 + 彩野测试 v0（第 2–3 段前就位）、预聚类 helper、F7 |
| 全量完成 | 末段裁决收出 **v8** | 写 **P4 fable 成品 spec**（含 tr_note 注入、物理排除断言、fable 全量排期） |

## 7. 风险与对冲

1. **notes 覆盖面＝裁决天花板**（opus 没提的问题裁决不会发现）→ 机器横扫独立双轨供料（§4 F10 行）。
2. **数周多会话连续性**（每段新会话接手）→ P2 的 handoff 模板固化为 `gen_plan.py` 的段间交接产物，含开场自检清单（§3）。
3. **额度争用** → 软政策 + 每周一次目测回顾，不建硬机制。
4. **段末裁决质量退化为即兴**（少量多次的反面）→ 饱和度闸门强制「证据不齐不裁」，预聚类 helper 保证每次面对的是整理过的卷宗。

## 8. 边界（本 spec 不覆盖）

- fable 成品车道的具体设计（P4 spec 另立）。
- 图片烤字轨、音频轨、注入回写（build/）工具链。
- 外部 API 翻译车道的正式建设（仅保证管道可扩展）。
- 窗口探针重做（P2 §4 的专项设计要求保留，待 P4 前评估是否需要）。
