# DeepSeek 审计能力设计（路线 3：自建最小 agent loop，固定流程优先）

> 定稿 2026-08-02，经 `/adhd` 发散（5 视角 30 点子）+ 逐项确认后落档。
> 上游：`docs/superpowers/specs/2026-08-02-p3-fullrun-policy-design.md` §5「API 路线里程碑 1」。
> 本 spec 覆盖第二个里程碑：把 DeepSeek 从「单次问答」升级为「能读资产、做交叉核对、产结构化清单」的审计能力。

---

## 0. 目标与非目标

**目标**：让 DeepSeek 承担「读若干资产 → 交叉核对 → 产出结构化清单」这一类任务。这类任务的共同点是**机器校验器结构上做不到、而人做起来又太慢**。第一个落地任务是 366 条译者手记的「承诺-履行」审计。

**非目标**（明确排除，避免范围蔓延）：

- ✗ 用 DeepSeek 做正文翻译定稿（它的位置不在这里；fable 文风更好、opus 手记更准）
- ✗ 让 DeepSeek 直接写 `anchors.yaml` / `glossary.*.yaml`（把裁决权交给单次不可复现的输出）
- ✗ 建通用 runner 抽象（只有一个任务时抽象是负债，等第二个审计出现再提取）
- ✗ 建 MCP server（YAGNI；只保证将来包一层就行）
- ✗ 993 页 `novel/` 小说图（**能力缺口**：DeepSeek 的 Anthropic 兼容端点文档明写不支持 image/document 内容类型，需另找视觉模型或先本地 OCR，属另一条线）

## 1. 为什么是这个形状（决策依据）

### 1.1 为什么自建 loop 而非现成方案

| 路线 | 判断 |
|---|---|
| Claude Code 指向 DeepSeek 的 Anthropic 兼容端点 | 需用户元层面介入（另开终端、配环境变量），且被 paseo 方案 dominate。**暂缓**，待用户方便时与 paseo 一并试 |
| OpenCode 等原生多 provider CLI | 本项目把「纪律写进文档和测试」当核心资产，另起一套规矩代价过大 |
| **自建最小 loop** | **采用**。理由见 1.2 |

### 1.2 自建 loop 的关键性质：只读工具面 ⇒ 血溅范围封顶

自建 agent loop 的通常风险是跑飞/死循环/误改。本设计把工具面限定为**全只读**，唯一的写操作（写报告）由任务层执行、不经过模型。因此**循环跑飞的最坏后果是报告不完整，而不是仓库被改坏**。这是敢自建的根本理由，也是本设计不可动摇的约束。

### 1.3 一个自我推翻：第一个任务其实不太需要 agent 循环

手记提案的实际格式已把 id 写在正文里：

```
### 1. 寝癖 → 睡翘的头发（**跨轨复现，优先级最高**）
- id 7327、7329、7332、7333、7335、7337、7359、7373（本批 8 处）
```

于是「取这些行的原文与译文核对承诺」这一步的上下文**可以由我们预先拼好**，模型无需自行决定调用哪个工具。

但不是全部：部分提案不写 id 只写「本段 8 处」；部分承诺要跨提案检索（「沿用 batch 2 提案 6 的规则」）；而**下一个审计任务（反向剧透红队）必须让模型自己决定读哪一段**——没人能预先知道哪句话会「语气泄密」。

**结论**：function calling 做**兜底能力**，不做主路径。预拼能覆盖的走预拼（便宜、可预测、易测）；覆盖不了的开工具。这样基础设施得到真实验证，而第一个任务不被基础设施拖慢。

### 1.4 paseo 的位置（决定工具层的契约形状）

paseo 文档原文：「A provider is the contract between Paseo and one external agent CLI: how to launch it, how to stream its output, how to send input back, what modes it supports.」「The actual binary lives on your machine and runs as a normal subprocess.」

**paseo 监管进程，不调模型 API**——它与 `api_client` 不在同一层，永远不会是 `api_client` 的「后端」。真正的集成点是另一句：

> 「Your subscriptions, your config, your skills, **your MCP servers all stay intact**.」

MCP 从底层 CLI 继承。所以「将来轻松接入 paseo」的正确含义是：**让领域工具能被 paseo 监管的那个 agent 够到**。据此，工具层设计为「一份实现、三个消费面」（见 §3）。

自建 loop 与 paseo 不是竞品：前者适合脚本化、确定性、可测、无需用户介入的重复审计；后者适合探索性 agent 工作。**二者共享的资产正是领域工具层。**

## 2. 能力层：`tools/api_client.py` 扩展

### 2.1 新增能力

- 支持在 Responses API 请求里发送 **function 类型的 tools**
- **有界**多轮工具调用循环：`max_rounds`（默认 6），达上限即停止并在返回值里标记 `stopped_reason="max_rounds"`（不静默截断）
- 每轮的工具调用与结果进入返回值，供任务层留痕

### 2.2 守卫改造（本节是硬约束）

现有三条断言：payload 无 `tools`、无 `tool_choice`、原始 JSON 串无 `web_search`。它们是当初为**防止彩野测试作弊**而建的闸——Responses API 内置服务端 `web_search`，一旦启用，受试模型可上网查本作剧情，不看译文也能答对，测试静默失效。

**加 function 工具会打破前两条。正确改法不是删断言，是收紧**：

1. `tools` 数组里每一项必须 `type == "function"`
2. 每个函数名必须在**白名单**内，白名单**从 `agent_tools` 的注册表取**（不手写第二份名单，避免两处漂移）
3. 原始 JSON 串不得含 `web_search` 字面量（此条**原样保留**，且它是改名绕过的兜底——历史上已验证能捕获 `builtin_tools` 这类改名尝试）
4. 彩野测试（`ayano_test`）**继续一个 tool 都不发**——它的受试者必须只靠给定文本作答

### 2.3 默认档位政策不变

沿用既有：`reasoning.effort=max`、`max_output_tokens=262144`、逐 chunk 静默超时、重试（4xx 不重试、429 读 `Retry-After`）、计费台账记 `effort`/`cached_tokens`/`reasoning_tokens`。

## 3. 工具层：`tools/agent_tools.py`（新）

### 3.1 契约

每个工具 = **纯函数** + **MCP 形状的 JSON Schema** + 一行描述，注册进 `TOOLS: dict[str, ToolSpec]`。`ToolSpec` 含 `fn` / `schema` / `description`。

纯函数意味着：不依赖全局状态、可用合成数据单测、可被任意消费面复用。

### 3.2 首批四个工具（全部只读）

| 名字 | 输入 | 输出 |
|---|---|---|
| `get_lines` | `ids: list[int]` | 各 id 的原文 jp、现行译文 zh（无译文则标注）、章别 |
| `search_lines` | `keyword: str`, `scope: str`（章别或 `all`）, `limit: int` | 命中行的 id + jp + zh，**限量返回** |
| `get_note_proposal` | `chapter: str`, `batch: int`, `num: int` | 该提案块原文 |
| `get_anchor` | `id: int` | 该 id 是否为锚点、锚点 zh 与 recall 说明 |

数据源：`data/ledger.jsonl`、车道 `forward.jsonl`+`patches.jsonl`（经 `resolve_map`）、车道 `notes/*.md`（复用 `cluster_notes.parse_notes`）、`skeleton/anchors.yaml`。

**全部只读**。工具层不含任何写操作。

### 3.3 三个消费面，同一份实现

1. **Python 直调** —— 我们的 loop 用。**现在做。**
2. **CLI 子命令** —— `uv run python tools/agent_tools.py get-lines --ids 9441,9460`，JSON 输出。**现在做。**
   理由不只是为将来铺路：**它让人能用同一份工具手动复算模型看到的东西**。对一个反复强调「不要恒绿关卡」的项目，这本身是纪律的一部分。
3. **MCP server** —— **现在不做**。schema 已是 MCP 形状，将来包一层即可。

## 4. 任务层：`tools/audit_notes_promises.py`（新）

### 4.1 要审什么

手记里记着大量**显式翻译决定**（「此处保留歧义」「照原样保留待判」「须逐字一致」「已按 X 译法统一」），**从来没有人回头查过它们是否真被执行**——甚至可能在后续批次被无意识违反。

这不是审计文本质量，是**审计决策的执行**。机器校验器结构上做不到。

### 4.2 承诺的抽取边界（用户裁决）

**只审硬承诺**（「照原样保留」「须逐字一致」「不消歧」「已按 X 统一」这类已作出的决定），**不审软倾向**（「建议」「宜」「可考虑」）。

理由：软建议本来就没许诺执行，审它会制造大量伪违约，把真违约淹掉——这与本项目反复吃过亏的「噪声掩盖信号」是同一种失败。

### 4.3 固定流程

- **步骤 1（无工具）**：从提案文本抽显式承诺 → `{承诺类型, 涉及 id, 承诺原文}`。无硬承诺的提案直接跳过。
- **步骤 2（预拼为主、工具兜底）**：取相关行的原文+译文，判断承诺是否被履行 → `{verdict, 依据行 id, 一句话理由}`。`verdict ∈ {已履行, 未履行, 无法判断}`。**id 缺失或需跨提案检索时才开工具。**
- **步骤 3（无模型）**：汇总 markdown 报告，**未履行优先排序**，`无法判断` 单列。

### 4.4 「无法判断」是一等公民

**不得强迫二元判定。** 一个把不确定硬判成「已履行」的审计器比没有更危险——这正是本项目这一轮反复踩的坑（卡组前缀使测试恒绿、静态数据无守护、分诊标记键控在不稳定产物上）。

报告里「无法判断」的占比本身就是可信度指标，须在报告顶部显示。

### 4.5「未履行」的四类归因（Task 9）

首次全量跑之后，控制器对当轮报出的 12 条「未履行」逐条独立复算（查 ledger 原文、
冻结骨架 `skeleton/`、`glossary/` 历史版本），发现它们**性质完全不同**，混在一栏
会让读报告的人把误报当真问题：

| 类别 | 判据（一句话） | 实测条数 |
|---|---|---|
| **真违约** | 译文没有落实手记声称已做的事——需要改译文 | 6 |
| **比对过严** | 模型字面匹配过死，其实已满足承诺（趋向补语/近义替换已蕴含承诺内容）——误报，无需改动 | 4 |
| **手记过时** | 该承诺已被后续 glossary 版本裁定取代，译文才是对的——该改手记而非译文 | 1 |
| **措辞过宽** | 手记写「一律」但实指某句族，非真正通则——酌情澄清手记措辞，译文不必因此改动 | 2 |

**设计判断：只让机器做机器能做的。** 不能让审计模型自己二次分类——它刚下完
「未履行」判定，再问它「你是不是过严了」，等于让它在同一口气里既下判定又质疑
自己，不可靠（同 §5.3 的教训：判定不可锚定在模型自陈的推理文本上）。四类里
**只有「手记过时」这一类有机械证据**：回改车道 `data/patches.jsonl` 记录了每条
回改的 `{id, zh, reason, glossary_v, ts}`，`reason ∈ {review, recall, polish}`：

- `reason=recall`（实测 id 7576，`glossary_v=8`）＝该行**因术语裁定被正式召回**，
  若手记写在该裁定之前，就是「手记过时」的硬证据。
- `reason=review`（本次审计后用户裁决产生的 4 条，`glossary_v=9`）＝该发现
  **已被处理**，构成闭环。

实现（`tools/audit_notes_promises.py` 的 `render_report`）因此**只呈现证据，不
自动改判 verdict，也不自动归类**：对每条「未履行」，检查其 `evidence_ids` 是否
被 `patches.jsonl` 覆盖，命中 `recall`/`review` 就在该条下面加一行机械标注（附
`glossary_v`），其余三类（真违约/比对过严/措辞过宽）没有机械线索，报告顶部只给
一份**人工分类清单模板**（四类名称+判据一句话），分类判断留给抽核的人。
`patches.jsonl` 路径按 `lane_dir` 参数解释，不写死仓库根；文件不存在时**显式
播报**「未检查」而非静默假装检查过——与 `check_batch.py` 里 W4 未启用时的播报
纪律同构（commit `3c0ab9c`，本项目刚修掉的第八例「恒绿闸」）。

**已知能力缺口（不在本次实现范围）**：长对话批量实验中发现，译者曾把一条并不
存在的规则写进手记并当作先例（把「彩野的 `ごめんね` 译作『对不起哦』」过度解读
成「该词组彩野专属」），见 `docs/superpowers/specs/
2026-08-03-long-conversation-batching-design.md` §5.5。**现有审计只核对承诺是否
被执行，不核对承诺本身是否成立**——「手记里写进了虚构的承诺」这一类审计不到，
记为能力缺口。

## 5. 验收：怎么知道它不是又一个「恒绿关卡」

本节是全 spec 最要紧的一条。

### 5.1 播种检验（硬门，不通过不上线）

人为构造若干**已知被违反**的承诺（改一份提案副本，使其与现行译文矛盾），确认审计报出「未履行」。至少覆盖三类承诺形态。**播种未被检出即视为不可用**，不得以「其余结论看起来合理」放行。

### 5.2 人工抽核

首次全量跑完后，由用户抽核若干条判定（含至少 2 条「未履行」与 2 条「无法判断」），确认判据与依据行站得住。

### 5.3 分诊标记的教训（不重蹈）

上一个 QA 工具的机械分诊标记因**键控在模型 run-to-run 可变的私有推理文本**上而被证伪（15 题打 10 个标记、与判分员疑虑反相关、当初为之设计的那题零标记）。

本审计的判定**必须锚定在可复算的事实**上：依据行 id、原文与译文的字面内容。CoT 可以记录供人读，**但不得作为判定依据**。

## 6. 成本与风险

**成本**：366 条提案，估计 ~100 条含硬承诺。步骤 1 批量约十几次调用；步骤 2 每条一次小上下文调用。缓存对步骤 2 帮助有限（每条上下文不同），绝对量在**几分钱**量级。

**风险与对冲**：

| 风险 | 对冲 |
|---|---|
| loop 跑飞 | 工具面全只读；`max_rounds` 有界；写报告不经过模型 |
| 审计恒绿 | §5.1 播种检验硬门 |
| 判定不可复算 | §5.3 判定锚定字面事实，CoT 仅留痕 |
| 白名单与注册表漂移 | §2.2 白名单从注册表取，不手写第二份 |
| 误伤彩野测试的防作弊闸 | §2.2 收紧而非删除；`ayano_test` 继续零 tools |

## 7. 边界（本 spec 不覆盖）

- 第二个及以后的审计任务（反向剧透红队、雾区审计、F13 引号内术语扫描等）——它们出现后再评估是否提取 runner 抽象
- 993 页 `novel/` 小说图（能力缺口，见 §0）
