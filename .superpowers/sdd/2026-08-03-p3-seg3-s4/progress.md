## ★会话组模式（b99–117）：一处结构性偏离及其裁决（2026-08-03）

> **本段是混合段**：b91–98 逐批产出、b99–117 会话组产出。日后做段内对照分析时**这是混淆变量**，
> 且本节记的偏离**只作用于会话组那一半**，对照时须一并计入。

### 发现：会话组计划的 Step 1「预生成全部批次 ctx」结构上不可执行

生成 b99–108 的 ctx 时，**只有 b99 成功**，b100–108 全部 `前缀行 13772 未译（--jp-fallback 可放行）` 退出码 2。

原因是 `build_context._render_prefix` 对窗口内每个前序 id 都要求已有译文，**否则整批拒绝产出**；
而 13772 正是 **b99 自己的第一个 id**。于是链条严格串行：

```
b99 译完 → append_forward(b99) → 才能 build_context(b100) → 才能有 b100/source.jsonl
```

**`gen_plan` 渲染的会话组 Step 1 把一组的 N 条 build_context 并列成一步，与该串行性冲突。**
长对话 spec §4.4 的原话是「ctx **照常逐批生成**」——spec 没错，**是计划渲染层把「逐批」读成了「可并列」**。
→ **开发轨待办**：`gen_plan` 的会话组 Step 1 应改为「逐批、在上一批入线后生成」，或显式写明本节的处置。

### 次生冲突：长对话与「每批立刻入库」不可兼得

Workflow 的 `agent()` **无法在中途暂停/续跑**，所以一条长对话没法和派发方的逐批
`append_forward` 交错。会话组模式实际上隐含要求二者让其一（spec 未讨论此点）。

### 用户裁决（2026-08-03）：jp-fallback 预生成 + 组末逐批入库

采用方案：

1. 用 `--jp-fallback` 预生成 b100–108 的 ctx，**目的仅是让 `source.jsonl` 就位**
   （`source.jsonl` 只由 `batches.jsonl`+`ledger` 决定，**与 fallback 与否无关，逐字相同**）；
2. 派发时**明令译者不得读 b100–108 的 `context.md`**（会话模式本就不读；那 9 份的第二节含 `〔未译|…〕` 占位）；
3. 整组译完后，派发方按批号顺序对每批：**先以正常模式重新生成该批 ctx**（覆盖 fallback 档案、取真 `ctx_sha`）
   → `check_batch` → `detect_collapse` → `append_forward` → commit。

**因此入档的 ctx 与 `ctx_sha` 最终都是真值，审计链不留 fallback 残迹。**
