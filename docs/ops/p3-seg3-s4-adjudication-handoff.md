### 执行流程（runbook §5「裁决会话清单」7 条，每条挂着实测坑）

**第 1 步 · 聚卷宗**

```
uv run python tools/cluster_notes.py --lane-dir pilot/lanes/opus --out work/out/dossier-seg3-s4.md
```

- 卷宗里判**「未匹配到该词键（可能提取不干净，请人工核对）」**的词族＝饱和度算出 0/0，
  **不等于「原文里没这词」**——要么词键真没出现（活用形/复合短语），要么标题没提干净。**一律人工核对原标题后再定。**
- 若打印 **「!! 告警：N 条提案没解析到批号（渲染为 bNone）」**，说明有 notes 文件的批次标题不是
  `^## batch <数字>` 形。**本会话已修过一次**（s4fa/s4fb 两个新建文件曾用 `## 会话组 b109–111`／`## 批次 116`，
  害 28 条提案丢批号）。**再见到就照同样办法修标题前缀，别忽略——批号是裁决时定位证据的唯一线索。**

**第 2 步 · 算饱和度**

```
uv run python tools/saturation.py --terms-file <本段提案词表> --data-dir pilot/lanes/opus/data --gate 0.8
```

- ⚠ **`--data-dir` 是这条命令最容易漏抄的一节。** 漏传会去读仓库根 `data/`，那里没有车道 forward.jsonl，
  于是按「零条已译」算出一张全列 `0.000 / 滚存` 的**完全合理的假表**。
  工具会在表头**之前**打印 `done=<N> 条已入线译文（data-dir=…）`——**N 应为 10864**；N=0 就是漏传了。
- 手抄词表**按词分行，不要整串抄并列词**（`はい／いいえ` 这类）。工具会自动拆并列词并提示，但多一轮核对。
- 词表带进残渣（裸 id、简体字、描述性前缀）会判「未匹配到该词键」，**同第 1 步，不等于「无出现」**。

**第 3 步 · 术语登记纪律（v7 起强制）**

`active.json` 每新增一条，**先算它对已入线译文的 W2 命中率再定稿**；值＝可字面校验的核心串。
**本段新增要求（输入清单 #3）：键也要覆盖排版变体**（中黑/长音/送假名的常见异形）。

**第 4 步 · 产出 glossary v10 + 召回令；回改走 patches**

- 回改用 `tools/add_patch.py`（或直接追加 `patches.jsonl`，字段 `{id, zh, reason, glossary_v, ts}`；
  `reason` 现有取值 `recall` / `review`）。

  ⚠ **`resolve.py` 只认 `ZND_DATA` 环境变量、没有 `--data-dir`**；主仓裸跑会读不到车道 forward，
  还会把一份空的 `final.jsonl` 写进仓库根 `data/`。
  ⚠ **本会话已产出 4 条 `reason=review` 的 patches（13567/784/13930/14148），复验时它们应当在 `final.jsonl` 里。**

**第 5 步 · ★每条回改必须落在「译者看得见的面」上**（v9 体例 `recall-must-be-visible`）

译者看得见的面**只有三个**：`active.json`、`style.md`、`voices/*.md`（`build_context._render` 的注入面）。
**三面都无处安放的回改**（纯语感/纯本地化、产生不了任何可登记词条），
**必须在 `pilot/lanes/<lane>/data/notes/<chapter>.md` 追加显式记录**：id、旧译、新译、一句话理由，
并注明「**旧文本作废、勿沿用**」。

> 起因：forward 是 append-only、**patches 只是覆盖层不回写前缀**，被否决的旧译法仍会在下游批次的
> **前缀正文**里现身，可能被当成先例照抄。
>
> ⚠ **维护者记录用 `##` 段落 + 表格写，不要用 `### 序号. 词 → 译` 形式**——后者是 `cluster_notes.py`
> 的提案标题格式，会把维护者记录算成新提案。
> **本会话已按此体例回填 4 条**（`notes/s4s.md` 3 条、`notes/crd.md` 1 条），可直接照抄格式。

**第 6 步 · 段边界版本切换（双车道）**

顺序：**漂移预检 → 双车道 `lane_setup --force` → `--verify` 无漂移 → 冻结内容抽验 → commit manifest+台账**

⚠ 三条实操陷阱，前两条是 seg1-s2 与 seg2-s3 各踩出来的：

1. **漂移预检必须用 `diff -rq <仓库侧> <车道拷贝>`，不能用 `--verify` 代替**——
   `--verify` 比对的是「车道拷贝 vs manifest」，**看不见仓库侧的改动**，此时它照报「无漂移」。
2. **`--force` 单独给不够**：`lane_setup` 建/重建车道要求同时给 `--lane/--model/--effort/--append-model-id`，
   取值照抄各车道现有 `lane.json`——**opus: opus/max/claude-opus-5；fable: fable/high/claude-fable-5**，否则直接报错退出。
3. **冻结面缺口（未修，属开发轨待办）**：`lane_setup.freeze_hashes()` 只哈希 5 项
   （`batches`/`cards_zh`/`anchors`/`active`/`glossary_max`），而 `COPIED_DIRS=("skeleton","glossary")`
   会把 **`speakers.json`、`style.md`、`voices/*.md` 一并拷进车道冻结**——
   **这三类被冻结却不在 manifest 里，`--verify` 结构上检测不到它们的漂移。**
   **凡本次召回令触及这三类文件**（本段输入清单 #4/#5/#6/#7 全都指向 `style.md`，**几乎必然触及**），
   **抽验步骤必须显式读车道拷贝确认内容**，不能只看 `--verify` 的绿字。
