# `png/scene/` 版面测绘规格

烤字回填第二块：场景名条集（`scene_1_a.png`/`scene_2_a.png`）。本文档记录版面
测绘的**方法与证据**，供 `tools/bake_scene.py` 实现依据。方法论沿用
`build/plot_layout_spec.md`（第一块 `plot/` 的成品），但**不假设任何具体数字可以
直接复用**——3 列 vs 6 列、每 102 张卡换页 vs 每 60 张、纯色底 vs 照片底，逐条
重新测量。

## 0. 文件清单与一个先要查清楚的疑点

`png/scene/` 有 4 个文件：`scene_1_a.png`、`scene_2_a.png`（`.gim` 名义资源，被
`lua_scripts/snr_common.lua:5059-5060` 的 `cGetFileName("scene", "scene_1_a")` /
`"scene_2_a"` 实际加载），以及 `__scene_1_a.png`、`__scene_2_a.png`（双下划线
前缀）。

**`__` 前缀两张是什么**：全仓库 `png/` 树里唯一带 `__` 前缀的文件就是这两张
（`find png -iname "__*"` 只命中它们），且 `grep -rn "__scene" lua_scripts/`
**零命中**——没有任何 lua 脚本引用这两个文件名，游戏运行时不会加载它们。

比对 `__scene_1_a.png` 与 `scene_1_a.png`：
- 尺寸/内容布局完全一致（435×510，同样的 195 张卡文字、同样的位置）。
- **`__` 版本是 `RGBA` 模式（无调色板）；正式版本是 `P` 模式（带逐调色板项
  alpha 的满 tRNS 表）**——与 `plot/` 的调色板形态相同，即正式版本是 `.gim`
  转换链路的**输出产物**，`__` 版本更像转换前的中间产物。
- 全图逐像素比较：**RGB 分量在任意一个像素上都完全相同**（`(0,0,0)`——因为
  这批图本来就只有黑色内容，见下第 3 节），差异**只出现在 alpha 通道**，且
  仅占 34511/221850≈15.6% 的像素（集中在文字笔画与四角缺口的抗锯齿过渡带），
  最大差值可达 255（例如同一坐标一边是 alpha=153 一边是 255）。

**结论（把握程度：高）**：`__scene_*_a.png` 是 `.gim`→`png` 转换流程留下的
**未量化中间产物**（大概率是调色板量化前的原始 RGBA 渲染，或转换工具的另一次
导出），RGB 内容与正式版完全一致，只是 alpha 精度/取整方式不同（P 模式量化到
调色板项的离散 alpha 值时发生了取整偏移）。它**不是游戏引擎会加载的资源**，
本仓库其余文件夹里没有出现过这种"影子文件"模式，`plot/`/`card/`/`select/` 等
其他资源夹都没有对应的 `__` 版本。**处置：保留原样，不烘焙、不产出对应的中文
版本**——它对最终中文化没有任何用途（引擎从不读它），本任务只在此记录发现，
不修改这两个文件（`png/` 本身也是只读原始资产）。

## 1. 基础网格

**测法**：`PIL Image.open(...).size` 直接读取。

```
scene_1_a.png  435x510  P（调色板，满 tRNS 表）
scene_2_a.png  435x510  P
```

CLAUDE.md 记载「145×15 格，3 列」。435/145=3（整除），510/15=34（整除）——
算术自洽但只是必要条件。**权威证据在 lua 源码**：
`lua_scripts/snr_common.lua:955-984` 的 `sceneState` 构造循环：

```lua
sceneState = {}
v3 = 0; v4 = 0            -- col, row
v5 = layerName.scene_1_a  -- 当前 sheet
i4 = 1                    -- sheet 序号（用于 i4*102 判断换页）
for i8 = 1, 195, 1 do     -- i8 = 卡号
    sceneState[i8] = {}
    sceneState[i8].clipX = v3 * 145
    sceneState[i8].clipY = v4 * 15
    sceneState[i8].layerName = v5
    v9 = v3 + 1
    if 2 < v9 then v3 = 0; v4 = v4 + 1 else v3 = v3 + 1 end
    if i4 * 102 <= i8 then v3 = 0; v4 = 0; i4 = i4 + 1; v5 = v5 + 1 end
end
```

与 `plotState`（`plot/` 用）结构完全同构，只是参数不同：3 列（`2 < v9` 即
col 到 3 归零，对照 `plotState` 的 `5 < v6` 即 6 列）、每 **102** 张卡换页
（对照 `plotState` 的 60）。`layerClip(..., clipX, clipY, clipX+145,
clipY+15)` 消费点见下节——**145×15 的裁切矩形与"每 102 换页"都是运行时代码
写死的字面量**，不是猜测。

结论（高把握）：
- 每张 sheet：**3 列 × 34 行 = 102 格**，格宽 145px、格高 15px，铺满 435×510。
- 2 张 sheet 共 **204 格**，装 195 个条目，末尾 9 格空置（`sceneState` 循环
  的 `for i8 = 1, 195` 上界就是 195，不是 204——第 3 节会验证这 9 格确实
  全透明）。

## 2. 格号 → 内容映射（承重点）：域是 195 张卡，与 `plot/` 相同，**不是**
   「scene_title」454 行数据集

### 2.1 用途：Story 模式顶角"当前卡标题"角标 + Fragment 模式 cardLabel1

`sceneState` 在两处被消费，两处都用**卡号**索引，从未用过场景标题字符串本身：

1. `comSectionStoryStart(p0, p1, p2)`（`snr_common.lua:2012`，Story 模式
   讲述场景时调用）：
   ```lua
   layerCopy(layerName.scene, sceneState[sceneId2aCard[p0]].layerName)
   layerClip(layerName.scene, sceneState[sceneId2aCard[p0]].clipX,
             sceneState[sceneId2aCard[p0]].clipY, ..., ...)
   layerPosition(layerName.scene, 330, 5)   -- 屏幕(480x272)右上角
   ```
   `p0` 是 sceneId，通过 `sceneId2aCard[p0]` 转成**卡号**才去查
   `sceneState`——**p1（场景标题字符串参数）在这个函数体内完全没被使用**
   （它另有别的去处，见 2.3 节）。
2. `comSectionCardStart`（Fragment 模式做卡开场，约 `snr_common.lua:2489`）：
   ```lua
   savedataTitle(string.gsub(plotTitle[p1], "\n", ""), v1)
   ...
   layerCopy(layerName.scene, sceneState[p1].layerName)
   layerClip(layerName.scene, sceneState[p1].clipX, sceneState[p1].clipY, ...)
   ```
   这里 `p1` 直接就是**卡号**（`fragmentDoCardId`），且与 `plotTitle[p1]`
   在同一处被一起使用——**同一个函数、同一行代码块，`sceneState` 与
   `plotTitle` 共用同一个卡号索引**，是这批条带资源与 `plot/` 卡名缩略图集
   共享域的最直接代码证据。

### 2.3 反证：「scene_title」454 行数据集是另一条完全不同的运行时路径，
   不是这批图的来源

`build/extra_derived.jsonl` 里 `kind=="scene_title"` 的 454 行，`key` 形如
`"snr_e1_10_f:77"`（脚本名:行号），是**全仓库 229 个 lua 文件里所有
`scene_X(id, "标题")` 调用的字面量第二参数**的抓取结果——这是场景函数定义处
的参数名 `scene_title`（如 `scene_s1s_20 = function(scene_id, scene_title)`，
`lua_scripts/snr_s1_10_s.lua:33`），调用点例如
`scene_s1s_20(doScriptScene, "夏の朝、高校までの通学路")`
（`lua_scripts/snr_s1_10_s.lua:2649`）。

这个字符串参数确实被使用，但走的是**另一条运行时路径**：
`comSectionStoryBegin(p0, p1)`（`snr_common.lua:2373`）：
```lua
gameSave.sceneName = p1
gameSave.sceneId = p0
...
savedataTitle(p1, v1)               -- 存档列表 UI 文字，引擎实时字体渲染
comSectionStoryStart(gameSave.sceneId, gameSave.sceneName, gameSave.ayanoTime)
```
`p1`（scene_title 字符串）被存进 `gameSave.sceneName` 并喂给
`savedataTitle()`——**存档列表界面的副标题文字，由引擎实时用字体渲染，从不
烤进任何 PNG**。而紧接着调用的 `comSectionStoryStart(sceneId, sceneName,
ayanoTime)` 内部（见 2.1 节）**完全没有使用它收到的第二个参数**去索引
`sceneState`——只用 `sceneId2aCard[p0]`（卡号）。也就是说：这批 PNG 的域，
和「scene_title」454 行数据集的域，是**两个不同函数各自消费的两份完全独立
的数据**，只是恰好共用了 `scene()` 调用的同一批字面量字符串作为源头之一。

## 3. 「454 / 393 / 204 / 195」数量关系——完整解释（不含糊）

- **454**：`kind=scene_title` 的原始行数 = 229 个 lua 脚本里全部
  `scene_X(id, "标题")` 调用点的字面量标题参数抓取总数（一个场景在剧情 DAG
  里可能被多条分支路径各自调用一次 `scene()`，同一标题字符串因此会重复出现
  多次）。**这批数据的真实用途是 `gameSave.sceneName`/`savedataTitle()`
  存档列表文字，与本任务的 PNG 资源无关**（见 2.3 节的代码证据）。
- **393**：454 行去重后的唯一字符串数——多次重复调用同一标题字符串的场景
  合并后的结果，仍然是「scene_title」自己的域内去重，与 PNG 无关。
  （交叉验证：`build/extra_derived.jsonl` 里 169 行的 `source` 字段已被另一
  条流水线通过**精确字符串匹配**关联到某张卡的 `title_zh`，对应 155 个唯一
  jp 字符串、155 个不同卡号——这只是"字面量文本恰好等于某张卡标题"的部分
  重合，不是本资源的域定义，且 238 个唯一 jp 字符串完全没有关联到任何卡号，
  证明 393 这个集合本来就不是"195 张卡标题"的超集或子集，是另一个概念。）
- **204**：`scene_1_a.png` + `scene_2_a.png` 两张图的物理网格容量
  （2×102，见第 1 节）。
- **195**：本资源真正烘焙使用的域——`sceneState` 循环本身的上界（`for i8 =
  1, 195`），与 `plotTitle[1..195]` / `skeleton/cards.zh.yaml` 完全同域，
  204−195=9 格空置（第 3.1 节验证）。

**结论**：454/393 这两个数字描述的是一个**完全不同的运行时文字表面**
（存档列表副标题，引擎实时渲染，不在本仓库任何 PNG 里），本任务的正确中文
源是 `skeleton/cards.zh.yaml` 的 `title_zh`（195 条，与 `plot/` 完全同一份
数据），**不是** `build/extra_derived.jsonl` 里 `kind=="scene_title"` 的那
454/393 行。这是本任务最重要的一处修正：任务交办文档原先假设「454 条
scene_title 就是本任务的文字」，代码 + 像素证据不支持这个假设。

`scene_2_a.png` 裁出卡 196–204（`sceneState` 循环范围之外、但网格容量之内

## 4. 原文排版：字号、对齐、颜色、底色形态

**测法**：对多张已知卡号的格子，用「亮度阈值」扫描统计文字墨迹的行/列外接框
（详见第 5 节——这里不需要像 `plot/` 那样加"暗描边邻域"联合判据，原因见
第 5 节的判据说明）。

- **单行，不换行**：195 格全部实测**单行**——即使卡180/182 这类 15 字最长
  标题（`サクラの日記：７月（書きかけ）`）也是单行显示，纵向墨迹范围恒为
  `y0∈{3,4}`、`y1∈{10,11}`（195 格实测），从不出现第二行。15px 格高本来就
  容不下 `plot/` 那种双行版式。
- **水平居中，垂直居中**：与 `plot/` 的"左对齐顶对齐"不同。证据：
  - 单字标题（卡118「春」）墨迹 x 范围 68–76，格宽 145 的几何中心是
    72.5——完全对称居中，不是贴左边。
  - 最长标题（卡180/182，15 字）墨迹 x 范围 5–139，相对格子中心 72.5 基本
    对称。
  - 垂直方向 y0≈3、y1≈11，格高 15 的中心是 7.5，`(3+11)/2=7`，同样对称
    居中（不是贴顶）。
- **左右边距固定 ≈5px**：195 格墨迹的 `x0` 最小值恰好是 **5**（卡180/182
  这类最长标题），`x1` 最大值恰好是 **139**（同一批），从未有格子的墨迹
  跨出 `x∈[5,139]` 这个区间——这是自然测出的边界，不是拍脑袋设的安全边。
- **每全角字符前进量 ≈9px**：卡180（15 字）墨迹宽度 135px，135/15=9.0，
  精确整除；卡85/119「屋上」（2 字）墨迹宽度 19px（≈9.5/字）；卡115/124
  「アヤノ/サクラ」（3 字）墨迹宽度 27px（9.0/字）——多个样本交叉核对到
  同一个 ~9px/字的前进量。
- **文字颜色**：白色填充（`(255,255,255,255)`）+ 黑色描边
  （`(0,0,0,255)`/`(0,0,1,255)`），与 `plot/` 同一套 caption 字风格。

### 底色形态：**纯色半透明条带，不是照片**——这是与 `plot/` 最大的不同

`plot/` 每格背后是该卡对应场景的暗化缩略截图（照片内容，逐格不同）。
`scene/` **完全不是**：

- 把 `scene_1_a.png` 里卡1、卡2 两个相邻格子逐像素比较，**TEXT_BOX 之外
  的区域（含四角缺口装饰）逐字节完全相同**——换句话说，背景是跨格共享的
  同一份模板，不是每格各自的美术内容。
- 把卡1（sheet1）与卡150（sheet2，跨图跨内容）同样做 TEXT_BOX 外逐像素比较
  ——**依然完全相同**，证明这份模板对两张 sheet、全部 195 格统一生效。
- 逐像素统计（195 格全量扫描，剔除各格自身检测到的墨迹±1px 邻域后）：
  背景像素的 **RGB 分量恒为 `(0,0,0)`（100%，无一例外）**，只有 **alpha**
  在变化，其中 **98.9%** 精确等于 **153**，其余 1.1%（值 94/163/161，各
  780 次，195 格 × 4 次/格）集中在格子四角缺口的抗锯齿过渡带（见下）。

**四角缺口装饰**：格子四个角落各有一个小的半透明"凹口"（视觉上类似取景框
一样的边角标记，用 alpha 从 153 骤降到接近 0 再回升实现，RGB 始终是纯黑，
不需要额外的白色描边像素）。测得该凹口**只出现在 `x∈[0,4]∪[140,144]`
这两列区间**（左右各 5px），且只在行 y∈{1,…,4}∪{10,…,13} 附近有强度变化
（y=0/5-9/14 这些行即使在 x<5 也是纯背景 153，无凹口特征）。**195 格实测
墨迹从未进入 `x<5` 或 `x≥140`**，两者刚好互不重叠——这正是选定
`TEXT_BOX=(5,0,140,15)`（详见第 6 节）作为一个**全局固定矩形**（不像
`plot/` 需要逐格动态测算）就足够安全的直接证据。

**这意味着**：`scene/` 的擦除/替换策略比 `plot/` 简单得多——不存在"盖多了
就丢照片细节"的取舍，整个 TEXT_BOX 内部本来就是同一块纯色，覆盖多少都不会
损失任何美术内容，也就不需要 `plot/` 那套"逐格测墨迹高度、hard/soft 双档
色带"的复杂机制。

## 5. 墨迹检测判据：只用亮度阈值就够，不需要 `plot/` 的"亮+暗邻域"联合判据

`plot/` 因为背景是照片，必须要求"高亮像素周围紧邻描边黑"才能把真正的文字
墨迹从明亮背景（泳池、天空）里筛出来。`scene/` 的背景**恒为 RGB(0,0,0)**
（见第 4 节），不存在"背景本身很亮"这种情况，因此单纯的亮度阈值
（`min(r,g,b)>=200 and alpha>=200`）就足以准确定位墨迹，不会有假阳性——
这一前提本身也被测试钉住（`test_ink_bbox_of_cell_ignores_flat_background`）。

195 格全量跑：**195/195 检测成功，0 个检测失败，0 个墨迹越出
`TEXT_BOX=(5,0,140,15)`**（`tools/bake_scene.py::collect_ink_outliers`，
`tests/test_bake_scene.py::test_collect_ink_outliers_empty_for_real_data`
钉住这条回归——每次跑都重新验证，不是写死在文档里的断言）。

## 6. 本工具（`tools/bake_scene.py`）的渲染取值

- **中文源**：复用 `tools.bake_plot.load_titles_zh()`——即
  `skeleton/cards.zh.yaml` 的 `title_zh`（195 条，见第 2/3 节的域澄清）。
- **字体/字号**：`third_party/LXGWWenKai-Regular.ttf` @ **9px**。依据：
  该字体在 LXGWWenKai 下字号 N 恰好给出 N px/字的前进量与 N px 的字形高度
  （直接实测确认），与第 4 节测出的原文 ~9px/字前进量精确匹配——视觉当量
  匹配，不是拍脑袋。
- **TEXT_BOX = (5, 0, 140, 15)**：宽度 135px（对照原文墨迹从未跨出的
  `x∈[5,139]`，两端各留 1px 余量到 140/145 边界），高度取满格高 15px（原文
  墨迹 y∈[3,11]，取满格高比刚好包住 y∈[3,11] 的紧凑区间多留了上下各 2-3px
  缓冲，且第 4 节已确认四角缺口完全不进入 `x≥5` 区间，取满格高不会碰到装饰
  元素）。
- **居中渲染**：`ImageDraw.text(..., anchor="mm")`，锚点取 `TEXT_BOX`
  几何中心 `(72.5, 7.0)`——复刻第 4 节测出的水平垂直双向居中版式（这是与
  `plot/` 左对齐顶对齐**不同**的地方，别照抄 `plot/` 的排版参数）。
- **单行，无换行预算**：`MAX_LINES=1`——15px 格高结构性地不允许第二行
  （见第 4 节），`collect_overflow` 走 `tools/zh_wrap.py` 的 1 行折行+
  退让链，195 条真实 `title_zh` **0 条触发截断**（下方第 7 节展开）。
- **擦除策略：直接覆写像素，不做半透明合成**。`bake_cell()` 先用
  `ImageDraw.rectangle(TEXT_BOX, fill=(0,0,0,153))` **直接设置**
  `TEXT_BOX` 内每个像素的值（PIL 默认 `ImageDraw` 在 RGBA 图上是直接赋值，
  不做 alpha 混合，已用最小复现用例验证），而不是像 `plot/` 那样
  `alpha_composite` 半透明色带叠加在原图上——原因：原文墨迹本身是**不透明**
  的白色填充+黑色描边（`alpha=255`），若用半透明（如 alpha=153）合成盖上去，
  底下不透明的白色会按公式透出约 40% 的强度，形成肉眼可辨的灰色残影（本
  工具的 `test_bake_cell_alpha_composite_over_original_would_ghost` 用对照
  组量化复现了这个失败模式）。直接覆写像素则是完全替换，不存在混合残留。
  覆写之后再 `alpha_composite` 贴上新绘的中文文字层（该层本身透明区域
  `alpha=0`，不影响已覆写好的纯色背景）。
- **像素保真闸**：`find_outside_box_diffs(orig, new, TEXT_BOX)`——`TEXT_BOX`
  之外的像素必须逐字节不变，195 格全量跑批 **0 违规**
  （`manifest.json.pixel_preservation_violations`）。因为 `TEXT_BOX` 是
  全局固定矩形（不像 `plot/` 逐格动态），这条闸同时也在替我们持续验证第 4
  节"195 格背景模板完全一致"这条前提——如果哪天 `png/scene/` 的素材更新导致
  某格背景不再是纯色模板，这条闸会在那一格报违规，不会静默通过。
- **输出模式：RGBA，不强制转回 `P` 调色板**——与 `plot/` 同样的三点理由
  （见 `build/plot_layout_spec.md` 第 6 节），`.gim` 回转本轮不在范围内。

## 7. 超长标题：0 条命中，但机制齐全、会显式报出来

195 条 `title_zh` 在 `FONT_SIZE=9` / `TEXT_BOX` 宽度 135px 下**全部单行放得
下**，`collect_overflow()` 全量跑 0 条截断（`manifest.json.overflow == []`）。
最紧张的几条（右边距最小）：

| 卡号 | title_zh | 渲染宽度(px) | 剩余边距(px) |
|---|---|---|---|
| 182 | サクラ的日记：9月16日（夜） | ~123 | ~8（最紧） |
| 90 | 选择：烟花之下，与ユウイチ | ~117 | ~9 |
| 180 | サクラ的日记：7月（未写完） | ~122 | ~11 |
| 189 | サクラ的日记：11月12日 | ~101 | ~11 |
| 38 | 选择：对ユウイチ的心意 | ~99 | ~17 |

**这不是巧合，是结构性的**：中文标题普遍比原日文标题所需的全角字数更少
（中文不需要假名/助词填充，同样语义常常用更少字数表达），所以即使按原文
9px/字的视觉当量选字号，中文译文依然有 8–17px 的余量，不像 CLAUDE.md 交办
时预估的"大概率需要缩字号或截断"那样紧张。

**machinery 仍然齐全，不是靠"今天数据凑巧不超"就跳过实现**：
`collect_overflow()` 内部调用 `tools/zh_wrap.py` 的完整退让链（词边界重罚→
禁则降级→末位截断+省略号），任何一条 `title_zh` 未来改得更长导致真正超出
135px，会被这条函数捕获并在 `manifest.json`/CLI 输出里显式列出（`dropped`
字段给出被丢弃的原文子串），不会静默截断——
`test_collect_overflow_surfaces_truncated_titles` 用合成的超长字符串验证过
这条路径确实能触发和报出。
