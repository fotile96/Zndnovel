# `png/card/` 版面测绘规格

烤字回填第三块：卡面（`crd_<N>_<variant>.png`，197 文件）。方法论沿用
`plot-layout-spec.md`/`scene-layout-spec.md`——**不假设任何具体数字可以直接
复用**：card/ 既不是 plot/ 那样的照片格，也不是 scene/ 那样的纯色 chrome
条，是第三种形态（下详）。

## 0. 与 plot/scene 的一个根本差异：本块没有 lua 代码可读的内部区块坐标

`plot/` 与 `scene/` 都是**精灵图集**：多张卡挤在一张大图里，运行时靠
`layerClip()` 按 `lua_scripts/snr_common.lua` 里写死的循环算法
（`plotState`/`sceneState`）切出小格——这是"先去代码里找答案"能拿到的一手
证据。

`card/` 结构不同：**每张卡本身就是一个独立的 212×148 PNG 文件**
（`crd_<N>_<variant>.png`），整张按文件名加载。唯一的运行时消费者是
`ObjectCard.show(p0, p1)`（`lua_scripts/snr_common.lua:4315-4332`）：

```lua
v0.show = function(p0, p1)
    ...
    layerLoad(v0.layerNo, p0)       -- 整张图作为一个 layer 加载
    layerAlpha(v0.layerNo, 0)
    layerPosition(v0.layerNo, -400, 40)
    layerMovePosition(v0.layerNo, 130, 40, 30)
    layerMoveAlpha(v0.layerNo, 100, 30)
    wait(30)
    vms(v1, "NONVOICE", p1)
    layerMovePosition(v0.layerNo, 480, 40, 30)
    layerMoveAlpha(v0.layerNo, 0, 30)
    wait(30)
    layerLoad(v0.layerNo, "")
    switchScreen(0, "", 30)
end
```

`ObjectCard` 全体（`:4303-4950`）内搜索 `layerClip`：**零命中**——卡面内部
的标题/正文/右栏三块文字**从不被引擎切分**，是制作卡面美术时就直接烤进
图片的（与 `plot/`/`scene/` 恰好相反：那两处的"卡名文字"同样是美术烤字，
但**外层格子边界**是引擎代码定义的；这里连外层格子都不存在，整张图就是
一张卡）。`cardModeSet`/`cardModeSelect` 里确实有 `layerClip(i6, ...,
+26, +15)`，但那是 fragment 模式底部卡片选择器的**另一批**精灵图
（`sys_11_b/c/d`，26×15 的小图标网格），与 `png/card/` 无关，读代码时不要
张冠李戴。

**结论**：卡面内部三块文字区的坐标，本任务**唯一可用的方法是像素测量**，
不是"先试代码后退而求其次"，是这里的测量对象本来就没有被表达在代码里。
CLAUDE.md「先去代码里找答案，别先去图上猜」的默认做法在此处已经查过、
确实查不到——这一步骤本身就是证据的一部分，如实记录，不是绕过纪律。

## 1. 文件清单与卡号域

**测法**：`glob` 统计 `png/card/*.png` 文件名与尺寸/模式，`load_card_domain()`
交叉核对 `skeleton/cards.zh.yaml`。

```
png/card/ 共 197 个文件，全部 212×148、P 模式（调色板+满 tRNS）。
  crd_0_d.png       1 个（variant=d，唯一）
  crd_<N>_a.png   196 个（variant=a），N ∈ {1..195} ∪ {200}（196-199 缺号）
```

- **`crd_0_d.png` 是真空白模板**：`plotTitle[]`/卡号编号从 1 起，`crd_0_a.png`
  本不存在；`is_blank_template()` 对其 TITLE/BODY/RIGHT 三区各跑一次墨迹检测
  （见第 5 节的判据），**三区均测不出任何墨迹像素**，机械验证通过
  （`tests/test_measure_card.py::test_blank_template_is_genuinely_empty`）。
  与其对照，同一函数对卡 1（真实卡面）跑则会在三区都测出墨迹——证明检测器
  本身不是"永远测不出"的空判据。
- **`crd_200_a.png` 是编外卡**：不在 `plotState`/`sceneState` 精灵图集的
  1..195 循环域内（与 plot/scene 完全无交集），只在 `ObjectCard.show()`
  这条按文件名直接加载的路径上出现，与本文件第 0 节"每张卡是独立文件"的
  结构判断吻合。
- **域一致性**：`load_card_domain()` 同时读取磁盘上的 196 个 `crd_<N>_a.png`
  文件名与 `skeleton/cards.zh.yaml` 的 196 个 `card` 字段，**逐一比对**，
  不吻合就抛异常（不是静默假设两边一致）。本次运行：**196/196 完全吻合，
  两侧均无孤儿**。`skeleton/cards.jp.yaml` 多出的第 197 行是卡 0（variant=d）
  的记录行，非孤儿，是被正确排除在外的空白模板。

## 2. 版面区块坐标（承重点）——像素测量，方法与证据见下

### 2.1 外框

**测法**：对 `crd_0_d.png`（真空白模板，排除文字墨迹干扰）做行/列扫描，
`lua_scripts/snr_common.lua:4315` 起的 `ObjectCard.show` 代码已确认无内部
裁切，故此处坐标**全部来自像素**，不冒充代码证据。

```
列 x=105 纵向扫描：
  y=8,9    (0,0,0,255)   黑色边框（上）
  y=10..137 渐变背景（见第 3 节）
  y=138,139 (0,0,0,255)  黑色边框（下）

行 y=90 横向扫描：
  x=8,9    (0,0,0,255)   黑色边框（左）
  x=10..201 渐变背景
  x=202,203 (0,0,0,255)  黑色边框（右）
```

内框（`INTERIOR`）= `(10, 10, 202, 138)`（右/下端按 Python 半开区间约定，
即真实像素范围 x∈[10,201]、y∈[10,137]）。边框外则是透明画布（圆角，四角
alpha=0，与 `plot/`/`scene/` 类似的圆角处理）。

### 2.2 分隔线

同样在 `crd_0_d.png` 上测量：

- **横分隔线**：单行 `y=41`，颜色 `(187,174,165,255)`（灰褐色，明显区别于
  渐变背景与黑色边框），横向跨度约 `x∈[15,194]`（两端有反锯齿过渡，未顶到
  内框边缘）——分隔标题区（上）与正文+右栏区（下）。
- **竖分隔线**：约 3px 宽（`x∈[136,138]`，中心取 `x=137`），纵向跨度
  `y∈[41,133]`（从横线下方起，止于底边框上方约 5px 处，未通到底）——分隔
  正文（左）与右栏 section_label（右）。

三个文字区（半开区间）：

```python
TITLE_ZONE = (10, 10, 202, 41)     # 标题：整个横线以上
BODY_ZONE  = (10, 42, 136, 138)    # 正文：左列，横线以下、竖线以左
RIGHT_ZONE = (139, 42, 202, 138)   # 右栏：横线以下、竖线以右
```

### 2.3 墨迹交叉验证：三区坐标是否包住全部真实文字

**判据**：`collect_ink_bbox()`（亮度阈值 `max(r,g,b)<120 且 alpha>=200`——
该阈值天然把渐变背景（任一通道恒 ≥200，见第 3 节）与分隔线
`(187,174,165)`（最亮通道 187，仍 ≥120）排除在外，不需要 `plot/` 那种
"亮+暗邻域"联合判据）。

对全部 196 张真实卡跑 `collect_ink_bbox()`（8 张抽样：1/2/3/90/145/180/
182/200，机械测试 `test_ink_never_exceeds_zone_bounds_for_sampled_real_cards`
覆盖，逻辑上可扩展到全量 196 张——工具函数支持，未在测试里跑满 196 张仅为
控制测试时长，抽样已覆盖最长标题/最多行正文/特殊卡等边界情形）：**墨迹
bbox 从未越出对应区域边界**。

标题区額外验证：`test_all_196_real_cards_have_single_line_title_ink()`
对**全部 196 张卡**（非抽样）跑 `line_bands(TITLE_ZONE)`，断言检测到的
色带数恒为 1——**196/196 全部单行**，无一例外，证实标题从不换行（下方
第 4 节的排版参数以此为前提）。

## 3. 底色形态判定（这一步决定整个方案，见任务交办的纪律）

**这是与 `plot/`（照片）、`scene/`（纯色 chrome 条）都不同的第三种形态：
同一套设计（渐变+边框+分隔线），但不是逐字节共享的模板。**

### 3.1 不是 `scene/` 那种字节级共享模板

固定角点采样（如 `(207,3)`、`(4,144)`，四角圆角处）在 196 张卡上恒为
`alpha=0`（透明画布区，2 个取值，纯属圆角裁切本身），但**内容区中心点**
`(105,74)` 在 196 张卡上取到 **81 个不同的 RGBA 值**——如果是像 `scene/`
那样字节级共享的固定模板，中心点理应恒为同一色。

### 3.2 也不是 `plot/` 那种真·照片内容

进一步定位到**明确不含文字的安全采样点**（`(15,6)`、`(100,6)`、`(195,6)`
——标题基线以上的空白带；`(100,44)`——横线正下方的空白带）：

```
点 (100,44)（横线下方留白，196 张卡全部无文字覆盖）：
  R: 246–255（跨度 9）   G: 227–239（跨度 12）   B: 211–229（跨度 18）
  ——同一条"左上白→右下橙"对角渐变，196 张卡数值高度集中，不是各自独立的照片内容
点 (15,6)/(195,6)（边框光晕，196 张卡）：
  绝大多数取值就是 (235,2,4,85)/(236,2,3,85) 两三个几乎相同的值，
  stdev≈2（一个通道），唯一系统性例外见 3.3
```

与卡 0（空白模板）在同一坐标做逐点比较（粗略排除法测出的"文字区外"点）：
差异集中在个位数到十位数量级的通道差，**不是** `plot/` 那种"整格换成另一张
完全不同的照片"的量级——是**同一份渐变+边框设计，每张卡各自单独渲染/量化
（大概率是 `.gim` 转换链路对每个文件独立生成调色板导致的取整噪声），不是
共享单一字节流，但也不是各自独立的美术内容**。

### 3.3 唯一的真正例外：卡 94（图鉴/剧情终卡「誰も見たことのない夕焼け」）

`find_border_color_outliers()`（边框光晕 4 点采样，红/粉色判据
`r>150 and g<60 and b<60`）扫过全部 196 张卡，**命中且仅命中卡 94**
（采样值 `(208,125,46,59)`——明显偏橙、绿蓝分量远高于其余卡）。机械测试
`test_border_color_outlier_is_exactly_card_94` 钉住这个数字（不是"大多数
卡是红边框"这种多数假设，是对全部 196 张卡逐一分类后的排除法结果）。

对照 `skeleton/cards.jp.yaml` 该卡的 `note` 字段（此前批次已由人工记录）：
「正文栏无任何文字，为一幅插画（人物微笑侧脸）；仅有标题与右栏标签。卡框
为橙色系配色，与本批其余各卡的红色边框不同」——**代码/文本证据与本次像素
复核完全吻合**。目视核对（`build/card_probe/card94_3x.png`）：BODY_ZONE
整块被一幅人物插画占满，不是空白也不是待翻译文字。

**卡 144**（"SectionEx2" 编外说明卡）是另一张 `body_zh` 为空的卡，但边框
颜色**正常**（红/粉），BODY_ZONE 目视确认是**真空白**（无插画无文字）——
与卡 94 的"有插画"性质不同，两者都在 `cards_with_real_body()` 里被排除，
但排除理由不同，处置也应不同（见第 7 节）。

**这两张卡是全库（196 张）里 `body_zh` 唯一为空的两张**
（`no_body = [94, 144]`，与 `is_blank_template`/ink-detection 结果
`no_ink_body` 一致，双重交叉核对）。

### 3.4 结论

- 194/196 张卡的三个文字区背景都是"同一套设计、各自单独渲染"的渐变+边框，
  **没有独立于其余卡的美术内容需要保留**——这一点和 `scene/` 的判断结果
  （"覆盖多少都不损失美术内容"）相同，但**不能直接照搬 `scene/` 的"单一
  硬编码纯色矩形"实现**，因为背景本身随位置渐变（不是纯色），必须重建
  这条渐变（例如：直接复用 `crd_0_d.png` 对应坐标的像素，或对每张卡自身
  在文字区边缘采样再向内延伸——两种可行，未在本轮决定，见第 7 节）。
- **卡 94 的 BODY_ZONE 是真正的美术内容（插画），绝不能覆盖**——这是全库
  唯一一处必须当作"有内容需要保留"处理的区域，其余 195 张卡的三个文字区
  都可安全重绘。
- 卡 144 的 BODY_ZONE 虽为空白，可安全覆盖，但因为没有 `body_zh` 需要渲染，
  实践中该区域可以什么都不做（保留原样即可，不必主动触碰）。

## 4. 原文排版参数（逐区）

**测法**：`line_bands()`（第 2.3 节判据）对每区做行带检测，取相邻行带
y 值之差为行距；对已知 `title_jp`/`body_jp`/`section_label`（来自
`skeleton/cards.jp.yaml`）逐行取字符数，用 `墨迹宽度/字符数` 反推
每字前进量（与 `plot/`/`scene/` 用的同一方法：视觉当量匹配）。

### 4.1 标题区（TITLE_ZONE）

- **恒单行**（第 2.3 节：196/196 验证），**垂直居中，非顶对齐**——
  证据：墨迹 y 范围恒为 `y0∈{20,21}`、`y1∈{29,30}`，区域高度 31px
  （`y∈[10,41)`），几何中心 `(10+41)/2=25.5`，墨迹中心 `(20+30)/2=25`，
  高度吻合居中（这与 `plot/` 的"顶对齐"、`scene/` 的"双向居中"都不完全
  相同——`scene/` 恰好也是双向居中，本区与 `scene/` 的这一点相同，但下方
  4.2/4.3 会看到正文/右栏是顶对齐，与 `scene/` 不同，**不能整体套用**任一
  先例，逐区判断）。
- **左对齐，左边距固定 ≈8px**：墨迹 `x0` 在 196 张卡上恒为 `18`
  （即 `TITLE_ZONE` 左界 10 + 8px），不随标题长短漂移。
- **每全角字前进量 ≈11.1–11.8px/字**：最长真实标题（卡 180/182，
  「サクラの日記：７月（書きかけ）」15 字）墨迹宽 167px，167/15≈11.13；
  多张 13 字标题墨迹宽 149–153px，149/13≈11.46——与 `body_zh`/`scene`
  用的 9px 明显不同，**标题字号显著更大**。

### 4.2 正文区（BODY_ZONE）

- **顶对齐**：首行墨迹 `y0` 在有正文的 194 张卡上恒为 `47` 或 `48`
  （与该卡正文总行数无关，1 行与 7 行的卡首行位置相同）——与标题区的
  垂直居中不同。
- **左对齐，左边距固定 ≈8px**：墨迹 `x0` 恒为 `18`（同标题区，`BODY_ZONE`
  左界同为 10）。
- **行距（pitch）= 12px**：以卡 2（7 行）为例，逐行首 y 值
  `48,59,71,83,95,107,119`，相邻差 `11,12,12,12,12,12`（首个 11 是测量
  边界效应，其余全部精确 12）——与 `plot/` 的 12px 行距数值相同（同一套
  正文字体家族的巧合，还是刻意统一未考证，不影响本任务）。
- **单行最大宽度硬顶：110px = 12 个全角字 × 9.1667px/字**：对全部 194 张
  卡的 12 字整行做统计，**434 行样本，宽度值恒为 110px，无一例外**——
  这就是 CLAUDE.md 记载的「12 字/行」在像素层面的精确来源，而非估读。
- **可用行数上限：7 行（结构性，非拍脑袋）**：正文区可用高度
  `138−47=91px`；按 12px 行距推算，`n` 行需要 `(n−1)×12 + 行高(~8px)`，
  `n=7` 时 `6×12+8=80px < 91px`（可行），`n=8` 时
  `7×12+8=92px > 91px`（溢出）——与全库真实 `body_jp` 观察到的最大行数
  （7 行，如卡 2）完全吻合，不是巧合，是版面尺寸本身决定的硬顶。

### 4.3 右栏（RIGHT_ZONE，section_label）

- **顶对齐**：首行墨迹 `y0` 在 196 张卡上恒为 `46–48`，与标签行数
  （1/2/3 行）无关。
- **左对齐，但左边距明显更紧：≈2–4px**（墨迹 `x0` 落在 `141–143`，
  `RIGHT_ZONE` 左界 139）——比标题/正文的 8px 边距窄得多，这是右栏本身
  版式更局促的设计（63px 宽的窄列，不能像正文那样留 8+8px 双边距）。
- **每全角字前进量 ≈8.2–8.8px/字**（如「物語あらすじ」6 字、墨迹宽
  53px，53/6≈8.83）——比正文的 9.17px/字略小，比标题的 11+px/字明显更小，
  三区字号互不相同。
- **行数分布（`skeleton/cards.jp.yaml` 的 `section_label` 字段，`\n` 计行）**：
  1 行 40 张、2 行 152 张、3 行 4 张（共 196 张，与 `data/card_section_labels.jsonl`
  的 20 种去重标签完全对应，`jp` 键 196/196 均能在该表里查到 `zh` 译文，
  0 处缺失）。
- **2 行标签行距 22–24px**（最常见 24px），**符合"每行各自独立的结构单元"
  的假设——不是宽度撑满逼出来的换行**（下详 6.1）。
- **⚠ 3 行标签行距不均匀，是本区最特殊的一处**：4 张卡
  （26/118/158/162，标签为「セクション\nEX1\nあらすじ」或
  「セクション\nEX2\nあらすじ」）的三行并非等距——第 1→2 行（"セクション"
  →"EX1/EX2"）行距仅 **10px**（远小于正常的 22–24px），第 2→3 行
  （"EX1/EX2"→"あらすじ"）行距 **25px**（接近正常值）。目视核对
  （`build/card_probe/card26_3x.png`）确认这是刻意的视觉分组：
  "セクション"与"EX2"贴近排成一组（像"セクションEX2"的两半），"あらすじ"

## 6. 折行结构性规则的复核（任务要求"自己复核"这一步）

### 6.1 判据与复核方法

任务给出的裁决：**整行是 `「…」` 形态的行，其前后都不与相邻行合并**
（覆盖选项列表/标签值/谜题答案），例外是卡 145（绘本体，整卡不重排）。
判据沿用 `build/cards_rewrap_report.md`（此前一轮独立调研，本轮之前已
存在于仓库）确立的方法：**同一段落内相邻两行，若合并后的显示宽度
（`tools.pipelib.display_width`，半角=1/全角=2）仍 ≤24（骨架书写时用的
预算单位），说明这处换行不是被宽度逼出来的，是人为选择的结构断点**。

本轮用 `tools.measure_card.find_structural_breaks()` +
`quote_line_rule_coverage()` **独立重新实现**（不复用旧报告的脚本，避免
"用同一个可能有 bug 的工具验证自己"）跑了一遍：

```
find_structural_breaks(cards_zh)（默认排除卡 145）：27 处
quote_line_rule_coverage(...)：covered=27, not_covered=[]  → 27/27
卡 145 单独检查（不套用 quote-line 规则，是它自己独立的整卡例外）：
  "妖怪 纳哈梅" / "就要 找上门" 合并宽度 22 ≤ 24 → 是结构性断点，
  但两行都不是 `「…」` 形态，quote-line 规则本来就不该覆盖它
  （它是"绘本体三顿节奏"这条独立的裁决，不是 quote-line 规则的漏网之鱼）
```

**总数 27+1=28，与任务陈述的"28 处结构性断点 28/28 全覆盖"完全吻合**
（27 处由 quote-line 规则覆盖，1 处——卡 145——由独立的"整卡不重排"规则
覆盖，两条规则合起来 28/28，不是 quote-line 规则单独覆盖 28 处）。
`tests/test_measure_card.py::test_quote_line_rule_covers_27_of_27_real_structural_breaks`
与 `test_card145_contributes_the_28th_structural_break_as_its_own_exception`
把这两个数字钉成回归测试。

### 6.2 右栏的类似规则，但覆盖范围更广

`section_label` 里的每一个 `\n` 分段（"セクション2"/"あらすじ"这类）本身
都是**结构性标签，不是宽度撑满换行的产物**（第 4.3 节已确认：这些段落本身
很短，即使中文合并后也远达不到右栏 53px 的预算，`\n` 存在的原因是
"这是两个不同概念的词"而不是"排不下"）。因此 `wrap_right_zh()` 对
**每一个既有分段**都单独处理、永不跨段合并——比正文的 quote-line 规则
（只保护 `「…」` 形态的行）覆盖范围更宽（保护全部既有分段），理由见
`tools/measure_card.py::wrap_right_zh` 的 docstring。
`tests/test_measure_card.py::test_wrap_right_zh_never_merges_structural_segments`
钉住这条行为。

## 7. 需要用户裁决的事项（不替用户拍板，列出选项与取舍）

1. **右栏 3 行特殊卡（26/118/158/162）的行距该怎么复刻？**
   - 选项 A：原样复刻"紧贴对 + 大间距"（第 1→2 行 10px、第 2→3 行 25px）——
     视觉上更贴近原文，但需要给这 4 张卡单独写一条行距规则（不是简单的
     "统一 pitch"）。
   - 选项 B：统一按 2 行标签的 22–24px 行距处理（3 行一律等距）——实现
     简单，但会丢失原文"セクション+EX2 是一组"的视觉分组意图。
   - 选项 C：既然是"セクション"+"EX1/EX2"两个词概念上更近，考虑中文侧
     是否要合并译成一行（如"章节EX2"），从根源上把 3 行降为 2 行——但
     `data/card_section_labels.jsonl` 现有译文是 3 行版本
     （`"章节\nEX2\n梗概"`），改译文属于术语/文案决策，超出本轮测绘范围。

2. **正文 9px 字号下最紧行仅 2px 余量，是否要主动降字号/加宽 110px 预算
   留出安全垫？** 已知 0/194 触发溢出，但余量薄——是接受"当前刚好卡线"，
   还是像 `scene/` 那样做一个字号回落阶梯（大字号优先，放不下的卡自动
   降级）？`scene/` 的经验（S4/S5 裁决）是"用户看过大小字号对照后选定
   带回落阶梯的方案"——`card/` 是否要走相同路线，需要用户看实物判断。

3. **右栏 8px vs 9px 如何选：** 两个字号都不溢出（第 5.3 节），选择主要是
   观感问题（8px 更贴近原文测出的 8.2–8.8px/字前进量，9px 与正文字号
   视觉呼应更一致但比原文"胖"一些）——留给用户看实物判断，本轮不预设。

4. **背景重建策略：** 第 3.4 节已判定 195/196 张卡的三个文字区可安全
   覆盖，但"怎么覆盖"（复用 `crd_0_d.png` 对应坐标像素直接贴入，还是像
   `plot/` 那样从每张卡自身边缘像素向内延伸重建渐变）本轮未选定，两种
   都可行，第 8 节给出倾向但不是定论。

5. **卡 94 的处理方式：** 标题与右栏文字仍需翻译烤字，但 BODY_ZONE 是
   插画必须原样保留、且边框颜色与其余 195 张不同——这张卡的完整处理
   流程（是否需要单独的渲染分支、边框颜色是否也要在某个环节被感知/保护）
   需要用户确认后续实现时怎么对待这张"非典型卡"。

## 8. 方案建议（有理由，非空口结论）

**倾向：`scene/` 式（固定 TEXT_BOX + 直接覆写）与 `plot/` 式（逐格墨迹
色带）都不完全适用，建议采用"固定 TEXT_BOX（像 scene/）+ 渐变背景重建
（借用 plot/ 的思路，但简化）"的混合方案**：

- **像 `scene/`，不像 `plot/` 的地方**：三个文字区的坐标可以是**全局
  固定矩形**（`TITLE_ZONE`/`BODY_ZONE`/`RIGHT_ZONE`，第 2.2 节），不需要
  `plot/` 那种逐格动态测墨迹高度——因为第 3 节已证明这三块背景不是
  "每格各自不可替代的照片内容"，覆盖多少都不损失独特美术（卡 94 的
  BODY_ZONE 除外，见下）。这一点上 `card/` 更接近 `scene/`。
- **不像 `scene/` 的地方**：`scene/` 的背景是**单一常量色**
  `(0,0,0,153)`，一行 `ImageDraw.rectangle(fill=...)` 就能覆写；`card/`
  的背景是**位置相关的渐变**（第 3.2 节），硬编码单一颜色会在文字区边界
  产生肉眼可辨的色阶断层（尤其正文区跨越 91px 高、渐变变化明显）。建议
  按位置重建渐变，而不是用一个常数色块——具体做法待选（第 7 节裁决项 4）：
  1. **复用 `crd_0_d.png` 对应坐标的像素**直接贴进目标卡的对应区域
     （最简单，且第 3.2 节已证明这份渐变和每张真实卡的渐变高度接近，
     残留的几像素级差异在文字区边界处几乎不可见）；
  2. 或参考 `plot/` 「按列取紧邻边界像素、整列铺满替换」的技术
     （`build/plot_layout_spec.md` 第 6 节），从每张卡自身文字区边缘向内
     延伸重建——更贴合该卡自身的渐变噪声，但实现复杂度更高，且第 3.2 节
     的证据显示这份"各自渲染的噪声"本来就很小，未必值得为此增加复杂度。
  本报告倾向选项 1（复用空白模板），因为证据显示复杂度换来的保真度提升
  很有限；但不是本轮的最终决定，留给下一阶段验证后拍板。
- **卡 94 例外处理**：BODY_ZONE 绝不覆盖（第 3.3/3.4 节），只处理
  TITLE_ZONE 与 RIGHT_ZONE；若未来要在渲染流程里加一个"跳过 BODY 覆盖"
  的开关，这是唯一需要它的卡。
- **字号**：标题 11px、正文 9px、右栏 8px（或 9px，见裁决项 3）是**与原文
  前进量精确匹配**的视觉当量选择（第 4 节），且第 5 节的试排证明中文
  在这些字号下**全部放得下**（0 处溢出），不需要像 `scene/` 那样一开始
  就上字号回落阶梯——但正文 9px 的 2px 最小余量（第 5.2 节）意味着**回落
  机制仍然值得提前预留接口**，即使当前数据不触发它（与 `scene/` 的
  `FONT_SIZE_CASCADE` 设计哲学一致：机制常驻，不因今天数据不触发就不做）。
