# `png/plot/` 缩略图：从「色带遮盖」到「干净底板重建」——方案研究报告（2026-09-07）

> 起因：测试反馈 `plot_1_a` 第二行第一格（卡 7「約束をしていない」→「没有约」）色带没盖住原文。
> 用户要求不止修这一格，而是趁 e2e 设施已就位，看看有没有更精细的做法（弄清每格背景怎么合成的、
> 自己合成或进游戏截图）。本文是这次研究的全部证据与方案。研究脚本在
> `tools/research/plot_plate/`（不在构建链路上），图在 `docs/ops/figures/plot-plate-2026-09-07/`。

## 0. 结论先行

1. **那格没盖住的根因**是墨迹检测的行阈值：第二行只有一个「い」，每行合格像素 1–2 个，
   低于 `INK_MIN_ROW_PIXELS = 3`，整行被判无墨。同病的还有卡 42、86、161，卡 170 半漏。
   全库 191 张的行数与「标题 ≤7 字一行、≥8 字两行」完全一致，按这条规则钉行数即可修，见 §1。
2. **缩略图怎么来的已经量清楚了**：`缩略图 = 0.5 × 游戏画面（bg / event CG / bg+立绘）→ 双线性缩到 82×48
   → 全表 256 色量化`。色调倍率 98 格实测 0.493±0.02、偏移 ≈ −1；换任何缩放滤镜差异 <0.15 RMSE。见 §2。
3. **由素材重建干净底板可行**：195 格里 178 格重建 RMSE ≤10（同一张图的量化地板约 4），
   42 格是纯黑底板（其中 40 张同一块板），另 12 格在 10–16（同一场景、立绘细节有差），5 格 >16 需单独处置。见 §3。
4. **模拟器截图路线**验证了合成器与引擎逐像素同源（同一状态 RMSE 都是 9.1），但作为生产手段不如
   合成器：受消息窗/时机污染、每格要开一次机。它的价值在验证与兜底，见 §4。
5. **推荐**：干净底板重建为主（§5 方案 B），色带修法为兜底与残余格处置（方案 A），模拟器做终检（§5）。
   本报告不动任何产物；两个方案的取舍等你裁。

## 1. 缺陷复盘：为什么「没有约」那格没盖住

`tools/bake_plot.py` 的色带高度取 `max(原文墨迹底, 中文渲染底)`；原文墨迹用「近白像素且 2px 内有近黑像素」
逐行计数，**一行 ≥3 个才算墨迹行**（`INK_MIN_ROW_PIXELS`）。卡 7 的日文「約束をしていない」8 字，
第 7 字断行，第二行只剩一个「い」——那一行在 82×48 的格里每行只有 1–2 个合格像素：

```
y16..y23  bright=1–2  dark≈50  pair=1–2     ← 第二行「い」，低于阈值 3
ink_bbox_of_cell → (3, 11)                   ← 只认出第一行
decision: content_bottom=16, band_bottom=20  ← 色带到 y=20 就羽化归零，「い」的 y21–23 露出
```

**全库普查**（`tests` 口径同工具）：

| 情形 | 卡 |
|---|---|
| 标题 ≥8 字、但只检出一行（第二行整行漏） | **7、42、86、161** |
| 两行检出但第二行只到 y=19（半漏） | **170** |
| 两行检出但第二行合格像素 <40（边缘） | 13、18、28、33、52、53、57、67、78、87、88、100、104、121、131、146、152、163、164、166、167、194 |

**行数规律**：195 张里，标题 ≤7 字的 79 张全是一行，≥8 字的 116 张全是两行（上面 4 张漏检的也是两行）——
即原图的断行规则就是「第 7 字后断行」，一个例外都没有。这条规则是数据上的确定事实，不依赖像素。

**修法（方案 A）**：行数由标题字数决定（≤7 → 一行，墨迹底 y=11；≥8 → 两行，底 y=23），像素检测降级为
交叉核对（检出的行数若与字数规则矛盾则报警，而非静默取像素）。改动只在 `decide_band`，
测试钉住那 5 张。效果见 `figures/…/card7_orig_current_quickfix_x6.png`（原图 | 现行 | 修后）：
修后色带盖到 y=28，「い」消失，代价是格子上半 58% 是黑带。

## 2. 缩略图是怎么合成出来的（实测）

### 2.1 色调：恒定 0.5 倍变暗

对 98 张「单图即可解释」的格（bg 或 event CG，无立绘），在无字行上最小二乘拟合 `缩略图 = g·源图 + o`：

| | g | o |
|---|---|---|
| 均值 / 中位 | 0.493 / 0.499 | −0.75 / −1.03 |
| 极值 | 0.425 … 0.518 | −3.3 … 2.4 |

固定 `g=0.5, o=0` 的 RMSE 为 4.57，逐格拟合 4.40，**没有一格固定倍率比拟合差 2 以上**。
event CG 与 bg 场景一律 0.5 倍——这是统一规则，不是逐格美工调整。

### 2.2 缩放：480×272 直接缩到 82×48，滤镜不可分辨

同一批格试 6 种滤镜 × 5 种几何（直缩 / 两级缩 / 裁边缩 / 缩到 82×46 补边 …），
均值 RMSE 全部落在 4.15–4.29：BICUBIC 4.17、BILINEAR 4.18、LANCZOS 4.28、BOX 4.2。
**地板 ≈4 就是 sheet 自身的 256 色板量化**（原 PNG 量化回 256 色损耗为 0，它已经是量化过的）。
故取 BILINEAR 直缩即可，再纠结滤镜没有收益。

### 2.3 内容：四个家族

| 家族 | 格数 | 判据 | 说明 |
|---|---:|---|---|
| 单张 event CG | 52 | 全 121 张 event 暴力匹配为最优 | 0.5× 直缩即得 |
| 单张 bg | 59 | 全 81 张 bg 暴力匹配为最优 | 含 4 张探索格（20/74/156/169）——**是裸地图底图**，不带地点条与人物（合成完整选点画面反而变差 10.5→12.6） |
| bg + 1–3 张立绘 | 41 | 场景函数配方合成 + 变体/位置搜索 | 立绘变体（表情）与位置要搜；引擎放置与合成器逐像素一致（§4），但**原缩略图的立绘比脚本位置偏 2–6 px（双人版式偏 8–16 px）**，说明当年截图状态与脚本首帧略有出入 |
| 纯黑底板 | 42 | 拟合倍率 ≈0 | 关键词卡 95–97/105–107/109/114–117/119–132、章节梗概卡 133–145、卡 1：**同一块板**（40 张两两 RMSE ≤1.7）：全黑 + 底部 3 行淡光（y45–47 均值 7/18）；18/55/173 三张是纯黑（开场即黑屏的场景） |
| 特例 | 1 | — | 卡 162 题名 logo 格 |

`_sel` 选择场景的缩略图**不含选项按钮**（卡 41/78 合成按钮后 RMSE 不变）。

### 2.4 配方从哪来

`lua_scripts/snr_*_10_*.lua` 每个 `local scene_<id> = function` 体内的 `layerLoad(layerName.bg1/event/poseN, cGetFileName(...))`、
`layerPosition`、`layerCopy(…, effectBlack)`、`comPoseLoad/comPoseDoubleLoad/comPoseInitPosition` 等按序求值，
得到各时刻的图层状态；缩略图对应的时刻**不一定是场景首帧**（150 张有场景函数的卡里，首帧状态 <8 的 37 张，
场景内取最优状态 <8 的 64 张；卡 47 在第 50 句、卡 146 在第 36 句才对上）。
配方之外再做暴力单图匹配兜底（38 张关键词卡没有场景函数）。

### 3.1 成品长什么样

`figures/…/demo_orig_band_plate_x3.png`：8 格 × 三列 = 原图 | 现行色带产物 | 干净底板 + 中文标题
（卡 7、9、20、47、90、133、152、194）。底板版里彩野/雪乃/教室/地图完整可见，标题白字黑边直接压在画面上，
与原版观感一致；色带版上半格是黑带。

### 3.2 封包量化代价

sheet 是 256 色索引图，改动越多量化越难。按 `build_disc` 同一条路径（FASTOCTREE 到 256 色 → GIM 往返 → `perceptual_mse`）：

| sheet 1 | 颜色数 | 量化损耗 |
|---|---:|---:|
| 现行色带产物 | 2 309 | 33.0 |
| 60 格全部换成干净底板 + 中文 | 44 325 | 38.5 |

多 5.5，与现行处在同一量级（原 PNG 本身 253 色、损耗 0）。要压这个数可以在烤字时先按 sheet 做一次 256 色量化预览，
或换 median-cut 量化，属实现期可调项；在游戏里这些格只有 82×48，肉眼阈值远高于此。

## 4. 模拟器路线的实测

- **首帧对照**（`probe_drive.py`，s1s_38 直入）：引擎画面缩到 82×48 后与卡 7 的 RMSE 9.1，与合成器按脚本位置
  合成的 9.1 **完全相同**——合成器对 bg+立绘的放置与引擎逐像素同源。因此原缩略图立绘偏 2–6 px 是当年截图状态的事，
  不是我们合成得不对。
- **逐句走场景**（`walk_drive.py`，s2s_150 直入、46 帧）：最像的一帧 RMSE 17.0（`m07`，恰好抓在换立绘的消息窗隐藏瞬间），
  而合成器广搜是 4.8。原因：帧里带消息窗/系统 UI，时机也随按键节奏漂移；要做生产用途得再加「压掉 UI 的测试叠加层」
  与按 `msg` 断点取帧的机制。
- 成本：每格一次开机 ≈15 s，逐句走一场景 ≈70 s；195 格全走约 1.5–2 小时机器时间，且仍需事后匹配挑帧。
- 附带发现：`--mode scene` 缺省预置全卡，进场先弹「跳过本场景？」对话框，取帧要加 `--no-cards`。

结论：模拟器**能**复现画面，但对本任务它是验证器不是生成器。它真正该承担的是最后一步——
把新的 plot sheet 装进测试盘，在 Story/Fragment 时间轴里看真实观感（`--mode mainmenu` 一次开机即可全看）。

## 5. 方案

### 方案 A：色带修法（最小改动）

- 改 `decide_band`：行数由标题字数决定（§1），像素检测降为交叉核对并报警；`tests/test_bake_plot.py` 钉住 7/42/86/161/170。
- 工作量：小（一个函数 + 测试 + 重烤 + 文档），无新风险。
- 局限：黑带仍盖住格子上半（一行 40%、两行 58%），画面信息被遮。

### 方案 B：干净底板重建（推荐）

**产物**：每格用素材重建 0.5× 的 82×48 底板，在上面按现行字号/描边烤中文标题；不再有色带。

**实现（新工具，`tools/bake_plot.py` 保留为兜底路径）**：

1. `data/plot_plates.jsonl`——逐卡冻结配方：`{card, kind: single|compose|flat|band, base: "event/eve_33_a" | "bg/bg_1_a_0", poses: [{name, x, y}], tone: 0.5, verify_rmse, note}`。
   由 `survey.py`/`refine.py` 生成初稿，人看拼图后定稿；残余格显式写 `kind: band`（走方案 A）。
2. `tools/bake_plot_plate.py`：读配方 → 合成 480×272 → BILINEAR 缩 82×48 → ×0.5 → **对照原格无字行算 RMSE，超过阈值（建议 12）拒绝**
   （防素材/配方漂移静默出错，与 `card/` 的 C5 重建闸同型）→ 烤中文标题 → 写 `build/plot_zh/`。
   纯黑底板用 40 张的中位数板；卡 162 单列（logo 保持日文，或用 `bg_21_c_0` + logo 合成，看图定）。
3. 测试：配方表覆盖 195 卡且每卡恰一种 kind；逐格 RMSE 闸；45 个空格逐字节不动；band 兜底格与方案 A 产物一致；
   sheet 量化损耗上限（按 §3.2 实测定阈）。
4. 文档：`bake-decisions.md` 新裁决（P5+）、`bake-specs/plot-layout-spec.md` 补「底板来源」节。
5. 终检：`build_disc.py --profile test --mode mainmenu` + 现有 `menu.py` 驾驶（或加一个翻时间轴的驾驶），看 4 张 sheet 在游戏里的观感。

**处置面**：178 格直接用（≤10）；12 格（10–16）拼图目检后决定「接受同场景近似」或降级 band；5 格 >16 先用 band，
有兴趣再逐张人工认图（41 尤其）。

**风险**：量化 +5.5（可调）；配方表是新一份需维护的数据（但有闸守着）；纯黑底板顶部 3–23 行没有实测依据（推定为黑，
与行间空白一致）。**工作量**：1–2 个工作单元（工具+数据+测试各半天，目检与文档半天）。

### 方案 C：模拟器截图为底板

不建议作为生产手段（§4）。若要做：test 叠加层把 `vms` 换成 `wait` 并隐藏系统 UI，在每个 `msg` 处 VRAM 取帧，
再用 §3 的匹配挑帧。适合处置方案 B 的残余格与最终视觉验收。

### 方案 D：从格内补绘（inpainting）

未实测。理由：B 已能解释 178 格，剩余格数少，补绘质量在有人物的格上不可控，优先级最低。
